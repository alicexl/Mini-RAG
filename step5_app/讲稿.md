# Step 5 讲稿：套一个聊天界面 —— 把 RAG 做成产品

---

## 一、命令行里的 RAG，离「能用」还差一层

前四步我们手里已经有了一个完整的 RAG：检索 → 拼 context → system 约束 → LLM 生成。但它跑在命令行里（`step4_rag/demo.py chat`），作为 demo 够清楚，作为「产品」有三处别扭：

- **得装环境、敲命令**：想用它的人得会开终端、装 Python、跑 `ingest`、再跑 `chat`。普通人到「打开终端」这一步就被劝退了。
- **答案一次性蹦出来**：`Generator.answer()` 是阻塞的——模型把整段答案生成完才返回。问一个问题要干等几秒，没有任何「它在想」的反馈。你看 ChatGPT 那种一个字一个字往外吐的效果，体验上好得多。
- **换文档要改命令**：想换一份年报问，得重新 `ingest <新路径>`。对会用命令行的人也只是「麻烦」，对不会的人就是「做不到」。

这一章就把这三处都补上，给 RAG 套一层 Web 聊天界面：**浏览器打开就能问、答案流式往外吐、左侧上传文档点一下就入库**。重点不在 RAG 内核（内核和 step4 完全一样），而在「产品化」到底改了什么、没改什么。

## 二、Gradio：最快的 Python Web UI

做 Web 界面可以用 Flask/FastAPI + 前端，但对一个 demo 来说太重了。**Gradio** 是专为 ML/LLM demo 设计的：纯 Python，几十行就能起一个带交互的网页，自动开浏览器、自动处理前后端通信。

它的核心是 `gr.Blocks`，三件套：

- **布局**：`gr.Row()` / `gr.Column()` 像搭积木一样摆组件（左右分栏、上下堆叠）。
- **组件**：`gr.Chatbot`（聊天气泡）、`gr.Textbox`（输入框）、`gr.File`（上传）、`gr.Button`（按钮）、`gr.Markdown`（文字）。每个组件就是一个可视化的数据容器。
- **事件**：`组件.事件(回调函数, inputs=[...], outputs=[...])`——某个组件上发生了动作（按下回车、点按钮），就调一个 Python 函数，把指定的输入组件喂给它，把返回值写回指定的输出组件。

一句话：**布局摆组件，事件把组件和 Python 函数连起来**。后端就是普通 Python 函数，不用写路由、不用碰 JS。

## 三、动手：三个产品化改造

RAG 的核心类（`Embedder` / `RecursiveTextSplitter` / `VectorStore`）和 `SYSTEM_PROMPT` / `build_context` 都和 step4 一样，本章不动它们（demo.py 里原样内联）。本章新增的代码就两类：**流式的 Generator** 和 **Gradio 的界面层**。

### 改造①：Web 聊天界面

用 `Blocks` 搭一个左右分栏的页面——左边文档管理，右边聊天：

```python
with gr.Blocks(title="Mini-RAG · 财报问答") as app:
    gr.Markdown("# Mini-RAG · 财报问答")
    with gr.Row():
        with gr.Column(scale=1):          # 左栏：文档管理
            status = gr.Markdown(_status_text())
            upload = gr.File(label="上传文档（md/txt）", file_count="multiple")
            btn_ingest = gr.Button("导入向量库", variant="primary")
        with gr.Column(scale=2):          # 右栏：聊天
            sources = gr.Markdown(_format_sources([]))
            chatbot = gr.Chatbot(height=460)              # 聊天气泡区
            msg = gr.Textbox(placeholder="提问…（Enter 发送）")
            send = gr.Button("发送", variant="primary")
```

`gr.Chatbot` 是「messages」格式——里面装的是 `[{"role": "user", "content": ...}, {"role": "assistant", "content": ...}, ...]`，左右气泡自动分边。`msg.submit(...)` 把输入框的回车连到回调：

```python
msg.submit(fn=respond, inputs=[msg, chatbot], outputs=[chatbot, sources, msg])
```

输入框一回车，就把「当前问题 + 聊天历史」喂给 `respond`，把它返回的新历史写回 `chatbot`、检索来源写回 `sources`、把输入框 `msg` 清空。

### 改造②：流式生成

产品体验的关键一步。step4 的 `Generator.answer()` 是一次性返回整段答案；这里改成**流式**——用 anthropic SDK 的 `messages.stream`，拿到一个流，逐片 `yield` 文本增量：

```python
class Generator:
    def answer_stream(self, system, messages, max_tokens=2048):
        client = Anthropic(base_url=self.base_url, api_key=self.api_key)
        with client.messages.stream(
            model=self.model, max_tokens=max_tokens, system=system, messages=messages,
        ) as stream:
            for text in stream.text_stream:        # text_stream 逐片吐文本增量
                yield text
```

和 step4 的 `answer()` 比，差别只在 `messages.stream` + `yield`——模型一边生成一边往外送，不用等整段拼好。注意 key 的处理也变了：step4 没 key 会 `input()` 交互式问；Web 服务没有 stdin，这里改为只认环境变量/常量，没配就在生成时抛错、由界面接住显示在气泡里（`respond` 里 `try/except`）。

Gradio 的流式套路：**回调函数本身写成生成器，每 `yield` 一次界面就刷新一次**。`respond` 把空助手气泡先亮出来，然后边收流式片段边往里填：

```python
def respond(message, history):
    retrieved = store.search(message, embedder, top_k=3)             # 检索
    context = build_context(retrieved)                               # 增强：拼 context
    sources_md = _format_sources(retrieved)
    turned = history + [{"role": "user", "content": message},
                        {"role": "assistant", "content": ""}]         # 助手气泡先空着
    yield turned, sources_md, ""                                      # 先亮出问题 + 来源

    for chunk in generator.answer_stream(SYSTEM_PROMPT,              # 流式生成
                                         history + [{"role": "user", "content": …}]):
        turned[-1]["content"] += chunk                               # 边收边填进助手气泡
        yield turned, sources_md, ""                                 # 每次 yield 界面刷新
```

每收一个片段就 `yield` 一次——用户看到的就是答案一个字一个字长出来。多轮对话也顺手支持了：把**已有历史 + 本轮（带参考资料）**一起塞进 `messages`，模型能接住「那 2023 年呢？」这种追问；检索仍只针对最新问题（朴素 RAG 的简化，见下一节）。

### 改造③：文档管理面板

换文档从「改命令」变成「点按钮」。左栏一个 `gr.File` 上传 + 「导入向量库」按钮，回调读上传文件、切块、入库（复用 step2 的 `RecursiveTextSplitter` + step1 的 embedding）：

```python
def ingest_files(file_paths):
    for p in file_paths:
        text = Path(p).read_text(encoding="utf-8")
        source = Path(p).stem                        # 来源名取文件名（同 step4 ingest 口径）
        chunks = splitter.split_text(text)
        store.add(chunks, embedder, metadata=[{"source": source} for _ in chunks])
    store.save(str(DATA_DIR))
    return _status_text()                            # 刷新左栏库状态
```

左栏顶上还常驻一个 `_status_text`——显示库里现有多少 chunk、已导入哪些文档，让用户随时知道「这个 RAG 现在知道什么」。再配一个「导入示例语料」按钮，一键导入 step4 已清洗好的盐湖股份 3 年年报，省得每次手动上传。

### 跑起来

```
set ANTHROPIC_API_KEY=你的智谱key
PYTHONUTF8=1 python step5_app/demo.py
# → 浏览器自动打开 http://127.0.0.1:7860
```

启动后状态栏是空的（`向量库：0 个 chunk`）。点「导入示例语料」：

```
向量库：234 个 chunk
已导入文档：
- 盐湖股份2023年年报（节选）
- 盐湖股份2024年年报（节选）
- 盐湖股份2025年年报（节选）
```

然后在右栏问「公司2024年赚了多少钱？」——检索来源先亮出来（Top-3，即 LLM 回答里「根据[1]」的出处），紧接着答案开始流式往外吐：

```
本次检索来源（Top-3）：
  1. sim=0.588  盐湖股份2024年年报（节选）  经营活动产生的现金流量净额（元）：2024年 = 7,819,152,860.43…
  2. sim=0.575  盐湖股份2024年年报（节选）  归属于上市公司股东的净利润（元）：2024年 = 4,663,116,528.38…
  3. sim=0.572  盐湖股份2024年年报（节选）  总资产（元）：2024年末 = 45,782,850,934.85…

助手（流式）：
公司2024年主要盈利数据如下：
1. 归属于上市公司股东的净利润为 4,663,116,528.38元（根据[2]）。
2. 归属于上市公司股东的扣除非经常性损益的净利润为 4,400,518,590.09元（根据[2]）。
```

这就是一个「能用」的 RAG 产品了：浏览器打开、上传文档、提问、看答案一个字一个字出来、每条答案都能追溯到出自哪份年报的哪个 chunk。整个过程没碰过命令行（除了第一次启动）。

## 四、套了 UI，它还是「朴素 RAG」

界面是好看了，但这一层只是壳——剥掉 Gradio，底下就是 step4 那个朴素 RAG。它还有几个生产级必须解决的工程问题：

- **状态在进程里，没并发隔离**：`store` 是个全局变量，所有用户共享同一个向量库。教学 demo 单人用没问题；真上线多用户同时提问、同时导入文档，就得加 session 隔离、并发锁、甚至把向量库挪到独立服务。
- **检索仍是最朴素的向量 Top-K**：没有 rerank 精排、没有混合检索（稀疏 + 稠密）、Top-K 里的噪音（第三问里那些相关但答非所问的块）照样喂给 LLM——step4 §四 列的那些检索层局限，套 UI 一个都没解决。
- **单机、无鉴权、无持久会话**：关掉进程对话历史就没了；任何能打开那个端口的人都能用你的 API Key；导入文档要等 Ollama 现算 embedding。

这些都不是「套个界面」能解决的，是 RAG 系统本身的工程化。本项目的定位是**先把朴素 RAG 的骨架从零走通、看清每一步**，到这里就完整了——检索、切块、向量库、增强生成、产品界面，五块全齐。

## 五、五步走完

回头看这五步：

1. **[Embedding](../step1_embedding/讲稿.md)**：文本变向量，余弦相似度找语义接近。
2. **[分块](../step2_chunking/讲稿.md)**：长文档切成 chunk，递归切分保语义边界。
3. **[向量库](../step3_index/讲稿.md)**：JSON + numpy 存 chunk 和向量，从零实现检索。
4. **[完整 RAG](../step4_rag/讲稿.md)**：检索 + 拼 context + system 约束 + LLM 生成，闭环 + 防幻觉两道关。
5. **聊天界面**（本章）：套 Gradio，流式 + 文档管理，做成产品。

一套朴素 RAG 的骨架就这么搭起来了。它每个零件都最简、都看得见——embedding 是一次 HTTP 调用、分块是递归切分隔符、向量库是余弦点积、检索是 Top-K、生成是拼 prompt 喂 LLM。没有黑盒。

> 想把这骨架做成能上生产的系统——混合检索、rerank、并发与隔离、持久化、让 agent 自己决定查不查查几轮——是下一个项目的事。但那些工程化，搭的都是「检索 → 拼 context → 生成」这个内核之上的能力。**把这个内核吃透，是后面所有花活的地基。** 这五步，就是把这个地基一行行码给你看。
