# Step 4 — 手写一个 Web 聊天界面：把 RAG 做成产品

> Flask Web 界面 + SSE 流式生成 + 文档上传 + 检索底座换 Milvus Lite + **PDF 多模态检索（正文/表格/图片）** + 分层评测集——浏览器打开就能问，答案一个字一个字往外吐，检索质量有数字。
> 四步路径与各步概览见仓库根目录 [README](../README.md)。

## 快速开始

前提：一个智谱 API Key（**embedding / 生成 / rerank / VLM 图片描述四者共用**，本步不再依赖 Ollama——检索嵌入已换成智谱 embedding-3，见 §2 改造④）+ `pip install -r requirements.txt`（本步新增 pymilvus / milvus-lite / pymupdf / pandas）。注意 Web 请求处理里没有 stdin，Key 只认环境变量 / 常量 / 启动时的交互确认（见 §2 改造②），没配会在生成时报错、以 SSE error 事件显示在聊天气泡里。另：Milvus Lite 一次只允许一个进程打开 `data/mini_rag.db`（文件锁），别开 Flask 的 debug reloader——它会起父子两个进程抢锁：

```bash
set ANTHROPIC_API_KEY=你的智谱key    # macOS/Linux 用 export
python -X utf8 step4_app/demo.py    # → 浏览器自动打开 http://127.0.0.1:7860
```

端口默认 7860，被占用时改 demo.py 底部 `app.run` 的 `port`。

## 1. 为什么要加界面，为什么手写 Flask

前三步我们手里已经有了一个完整的 RAG：两级检索（召回 + rerank 精排）→ 拼 context → system 约束 → LLM 生成。但它跑在命令行里（`step3_rag/demo.py chat`），作为 demo 够清楚，作为「产品」有两个硬伤：

- **上手门槛**：想用它的人得会开终端、装 Python、跑 `ingest`、再跑 `chat`——普通人到「打开终端」这一步就被劝退。
- **交互体验**：`Generator.answer()` 是阻塞的，问一个问题要干等几秒才有整段答案，没有任何「它在想」的反馈——不像 ChatGPT 那样一个字一个字往外吐。

这一步就是给 RAG 套一层 Web 聊天界面：**浏览器打开就能问、答案流式往外吐、左侧点「导入」从浏览器文件框里选文档入库**——降低上手门槛，提升交互体验。

界面怎么做？本 step 手写（Flask + 原生 HTML/JS）：多写一两百行，换来 Web 层完全摊开——URL 怎么映射到 Python 函数、静态页怎么被服务出去、流式答案怎么从后端一路推到浏览器的聊天气泡、文件怎么从浏览器传到服务端，每一环都看得见。

Flask 是 Python Web 生态的「最小公约数」，核心概念就四个：

| 概念 | 一句话 | 在 demo.py 里 |
|---|---|---|
| 路由（route） | 把 URL + 方法映射到一个 Python 函数 | `@app.post("/api/chat")` |
| 视图函数 | 被路由调用的函数，返回 HTML / JSON / 流 | `def chat(): ... return Response(...)` |
| 静态文件 | 浏览器加载的页面本身 | `send_from_directory(STATIC_DIR, "index.html")` |
| 请求对象 | 请求里带的东西（JSON 体 / 上传的文件） | `request.get_json()` / `request.files` |

整条链路就三段，各段都能单独抠出来看：

```
浏览器（static/index.html：渲染界面 + 发请求 + 解析 SSE）
   │  HTTP
Flask Web 层（demo.py：5 个路由）
   │  函数调用
RAG 内核（两级检索 → 拼 context → system 约束 → 生成；底座换 Milvus，见 §2 改造④）
```

## 2. 动手：六个产品化改造

前 3 步把原理摊开讲完了，这一步在产品化的同时做一次「零件升级」：`Embedder` / `RecursiveTextSplitter` / `Reranker` / `SYSTEM_PROMPT` / `build_context` 原样内联复用；**step3 手搓的检索三件套 `VectorStore`（JSON+numpy 余弦）/ `BM25Index`（手写 Okapi）/ `rrf_merge`（名次归并）整体退休**，换成一个 `MilvusStore`（见改造④）。新增的代码就两类：**流式的 Generator** 和 **Flask 的 Web 层**。

### 改造①：Web 聊天界面（路由 + 静态页）

Web 层一共 6 个路由，一张表看完：

| 方法 + 路径 | 干什么 |
|---|---|
| `GET /` | 返回 `static/index.html`（聊天页面） |
| `GET /api/status` | 库状态 JSON：chunk 数 + 已导入文档清单 |
| `POST /api/upload` | multipart 文件上传 → 切块 / 向量化 / 入库（幂等；PDF 走多模态解析，见改造⑤） |
| `POST /api/clear` | 清空向量库 |
| `POST /api/chat` | SSE 流式回答（见改造②） |
| `GET /api/media/<文件名>` | 回显图片 chunk 的原图（多模态，见改造⑤） |

```python
app = Flask(__name__, static_folder=None)   # 关掉 Flask 自带的 /static/<文件> 路由

@app.get("/")
def index():
    return send_from_directory(STATIC_DIR, "index.html")
```

`static_folder=None` 值得一提：Flask 默认会把 `static/` 目录自动挂到 `/static/<文件名>`。这里关掉默认行为、用 `send_from_directory` 手动返回页面——静态文件是怎么被服务的，亲眼看到这一次，后面再用默认行为就知其所以然。

前端就一个 `static/index.html`：无框架、无构建工具，CSS/JS 全内嵌。布局左右分栏——左栏文档管理（库状态 + 导入 / 清空），右栏聊天（检索来源面板 + 聊天气泡 + 输入框）。所有动态内容只用 `textContent` 写入（不走 `innerHTML`），chunk 原文按纯文本显示，顺带天然免疫 XSS。

### 改造②：流式生成（SSE）

`Generator.answer_stream` 和上一形态一样：用 SDK 的 `messages.stream` 拿到一个流，逐片 `yield` 文本增量。真正的新问题是：**HTTP 响应怎么「分多次送」？** Flask 的一次响应默认是送完即止的——那就让这一次响应本身变成流。这正是 **SSE（Server-Sent Events）**：`Content-Type: text/event-stream` + 一个生成器，Flask 每 `yield` 一段就往 socket 写一段。

协议自己定，四种事件，每帧两行头 + 空行结尾：

| 事件 | data | 时机 |
|---|---|---|
| `sources` | 本次检索来源（召回 20 → 精排 Top-3，带 `reranked` 标记） | 先亮来源 |
| `delta` | `{"text": "一小片答案"}` | 每个增量一帧 |
| `done` | `{}` | 回答结束 |
| `error` | `{"message": "..."}` | 生成中失败（无 Key / SDK 异常） |

```python
def stream():
    yield _sse("sources", {"sources": sources_payload, "reranked": reranked})
    try:
        for delta in generator.answer_stream(SYSTEM_PROMPT, llm_messages):
            yield _sse("delta", {"text": delta})
        yield _sse("done", {})
    except Exception as e:
        yield _sse("error", {"message": f"生成失败：{e}\n请确认 ANTHROPIC_API_KEY 已配置"})

return Response(stream(), mimetype="text/event-stream",
                headers={"Cache-Control": "no-cache"})
```

错误分两层，这是个值得记住的 Web 实践：**请求级校验**（空消息 / 空库）走 `400 + JSON`——那时响应头还没定，可以随便返；**流一旦开始**（响应头已是 `text/event-stream`）中途出错就只能往下写 SSE `error` 事件，前端把它显示在助手气泡里。

前端消费 SSE 用的是 `fetch` 而不是浏览器原生的 `EventSource`——后者只支持 GET，我们要 POST 请求体。解析器核心就十五行：`resp.body.getReader()` 逐块读字节 → `TextDecoder` 转文本 → 按**空行**切帧 → 帧内取 `event:` / `data:` 两行：

```js
const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buf = "";
while (true) {
  const {done, value} = await reader.read();
  if (done) break;
  buf += decoder.decode(value, {stream: true});
  let cut;
  while ((cut = buf.indexOf("\n\n")) >= 0) {      // SSE 帧以空行分隔
    const frame = buf.slice(0, cut);
    buf = buf.slice(cut + 2);
    /* 解析 event:/data: → 更新来源面板 / 助手气泡 / history */
  }
}
```

**多轮对话的状态放哪？** 前端持有一个 `history` 数组，每次请求随 body 带上来；服务端不存任何会话状态（无状态服务，重启不丢对话）。把「已有历史 + 本轮 user（带参考资料）」一起喂 LLM，模型就能接住「那 2023 年呢？」这种追问；检索仍只针对最新问题（朴素 RAG 的简化）。这也是聊天框架的 Chatbot 组件替你藏掉的那部分——现在它就摊在你的 index.html 里，约 15 行。

> 为什么不用 WebSocket？这个场景是「请求小、响应流」的单向推送，SSE 就是纯 HTTP，够用且更简单；WebSocket 的双向能力用不上。顺带一提：LLM API 自家的流式返回（OpenAI / 智谱）走的就是 SSE——这里的做法和生产同构。

### 改造③：文档管理（真上传）

导入语料从「敲命令」变成「点按钮」。页面里一个隐藏的原生文件框（`<input type="file" multiple>`，label 当按钮用），选中文件后前端拼 `FormData` 发 `POST /api/upload`，服务端从 `request.files` 里拿：

```python
files = request.files.getlist("files")     # multipart 里的文件列表
for f in files:
    source = Path(f.filename).stem          # 同 step3 ingest 口径：source 取文件名
    text = f.read().decode("utf-8", errors="replace")
    notes.append(_ingest_text(text, source)[2])
```

`_ingest_text` 逻辑同 step3：切块 → 向量化 → 入库，幂等——按文件名判断，已在库就跳过，不重算 embedding：

```python
def _ingest_text(text, source):
    if store.has_source(source):        # 库内标量过滤查询，替代 step3 扫 metadata 列表
        return 0, False, f"[SKIP]「{source}」已在库中"
    ...
```

值得强调的是「真上传」三个字：文件框由**浏览器**弹出（在你自己的电脑上选文件），内容随请求传到服务端——服务端只收内容、不碰服务端文件系统，**本地跑和部署到远端行为完全一致**。demo 框架图省事时常见另一种做法（服务端代码直接弹个框、拿本地路径读文件），本地演示看不出差别，一旦部署到远端服务器，框会弹在服务器上没人点。

### 改造④：检索底座工程化（Milvus Lite）

前三步的检索底座是手搓的：`VectorStore` 把余弦摊成矩阵乘、`BM25Index` 把 Okapi 公式写成循环、`rrf_merge` 把名次融合写成十行——教学价值就在「没有黑盒」。但它们毕竟是教具：线性扫描扛不住百万 chunk、BM25 索引每次启动现建、三件套要自己 save/load。工程端的答案是**向量数据库**——这里换成 Milvus Lite（Milvus 的嵌入式单文件版，`pip install milvus-lite` 即用，不用装服务）。概念与 step3 一一对应，零件换生产件：

| step3 手搓件 | Milvus 里对应的东西 |
|---|---|
| `VectorStore`：npy 存向量 + 归一化点积 | `vector` 字段 + HNSW 索引（`metric_type="COSINE"`），大规模走近似检索 |
| `BM25Index`：jieba 分词 + 手写 Okapi | `text` 字段开 jieba 分析器 + BM25 函数，插原文、库内自动分词建稀疏索引 |
| `rrf_merge`：名次折算 1/(k+rank) | `hybrid_search(..., ranker=RRFRanker(60))` 一个参数 |
| 三件套 save/load + 上传后重建 BM25 | 落库即持久化（WAL），稀疏索引自动更新 |
| 扫 metadata 列表判幂等 | 标量过滤查询 `filter='source == "xxx"'` |

一张 collection 把「原文 + 向量 + 稀疏 + 元信息」全装下，schema 建一次、之后只管插和查：

```python
schema.add_field("text", DataType.VARCHAR, max_length=65535,
                 enable_analyzer=True, analyzer_params={"type": "jieba"})  # 中文按词切
schema.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)      # BM25 函数的输出位，不用手填
schema.add_function(Function(name="bm25", function_type=FunctionType.BM25,
                             input_field_names=["text"], output_field_names=["sparse"]))
schema.add_field("vector", DataType.FLOAT_VECTOR, dim=1024)   # qwen3-embedding 维度
schema.add_field("source", DataType.VARCHAR, max_length=256)  # 来源文件名（幂等键）
```

检索侧两路各带一个 `AnnSearchRequest`，融合交给 `RRFRanker`——step3 里手写的那十行，在这里是一个参数：

```python
dense = AnnSearchRequest(data=[query_vec], anns_field="vector",
                         param={"metric_type": "COSINE"}, limit=20)
sparse = AnnSearchRequest(data=[query], anns_field="sparse",   # 查询原文进来，库内 jieba 分词
                          param={"metric_type": "BM25"}, limit=20)
hits = client.hybrid_search("docs", [dense, sparse],
                            ranker=RRFRanker(60), limit=20,
                            output_fields=["text", "source"])
```

**rerank 仍留在库外**（`retrieve()` 接着调智谱 rerank API）——精排要过一遍 Cross-Encoder 大模型，向量库不管这件事；失败降级回融合顺序，语义同 step3。

工程件不是白拿的，两个已知边界：

- **BM25 的 IDF 是 segment 局部统计**（官方已知限制），不是 step3 手搓的全库 IDF——分数有微小差异，排序影响可忽略。
- **单进程文件锁**：一个 data 目录同一时刻只允许一个进程打开——本 demo 单进程没事，但别开 debug reloader（父子两进程抢锁）。

「生产同款」的真正含义：把 `MilvusStore` 里的 db 路径换成 `http://localhost:19530`（Milvus Standalone，Docker 起）或 Zilliz Cloud 的 uri，其余 API 一行不改——教学件到生产件的迁移路径就是换一个连接串。

**embedding 换成智谱 API（本地 Ollama 在本步退役）**：前三步的检索嵌入一直是本地 Ollama（离线免 Key 的教学件）；这一步换智谱 embedding-3（与生成共用 Key，`dimensions=1024` 对齐 schema）。为什么换——实测（GTX970 Vulkan）：本地单查嵌入 ~2.2s，**占检索总延迟的八成**；换 API 后检索中位 2746ms → **912ms**。切换前跑了同一份评测集对比（§3）：**命中@3 持平（76.9%）**、答对 79.5% → 76.9%——丢的一分恰是 C06 那个「推算侥幸」case（本地版靠检索送来的产量/消费量现场算出 67%；换向量后送不上这两个数、如实答不出，反而更诚实）；Top-1 从 69.2% 降到 53.8%（精排第一名换了人，但都还在 Top-3 里，被生成层吸收）。**快 3 倍、端到端质量持平**——这就是「用评测而不是感觉做技术决策」的完整示范。代价两条：检索也依赖网络与 Key（丢掉「检索离线」，step1-3 的教学线不受影响）；换模型 = 向量空间不兼容，旧库必须清空重灌。

来源面板也随之变干净：不再显示 `sim`（向量相似度）和路由标记（手搓三段式的讲解道具），只留 `rrf`（库内融合分）+ `score`（rerank 精排分）+ 出处。

### 改造⑤：多模态检索（PDF 的正文 / 表格 / 图片）

到上一节为止，语料还是「纯文本 md 节选」。这一步让 `/api/upload` 直接吃 **PDF**：服务端解析出三种模态，塞进**同一个检索空间**——上传真年报，表格问题命中表格块、图片问题命中图片块。样例语料是 `sample_reports/盐湖股份2024年报（精选页）.pdf`：从 177 页的真年报里抽 10 页（脚本 `tools/extract_pages.py`，页集覆盖三种模态的代表性形态），库里产出 35 块 = 20 文本 + 4 表格 + 11 图片。

**解析管线**（`parse_pdf`，上传时同步跑）：每页用 PyMuPDF 抽三类元素——文本块（`get_text("blocks")`）、表格（`find_tables()`）、图片（`get_images()` + 落盘）——按 y 坐标排序还原成「带位置信息的元素流」，页眉页脚剔除、表格区内的重复文本块剔除、装饰图片（2pt 宽的侧边线、整页背景、同位叠放）剔除。然后按模态分流：

| 模态 | 检索用什么（text 字段，进 embedding + BM25） | 生成回填什么（content 字段） | 成块方式 |
|---|---|---|---|
| 正文 | 原文 | 原文 | 跟随元素流一起切 |
| 小表格（≤10 行） | 表格**文本化**（表头 + 逐行拼接） | **HTML**（保行列结构） | 边界标记内联，跟正文一起切 |
| 大表格（>10 行） | 文本化全文 | HTML | **独立成块**，正文留引导句 |
| 图片 | **VLM 描述**（glm-4v-flash） | 描述 + 原图文件名 | **独立成块**，正文留引导句 |

三个关键设计，每个都对应一个「为什么」：

- **embed 用文本化、生成用 HTML**——LLM 读 HTML 表格的理解远好于线性化文本，但 embedding 和 BM25 吃 HTML 标签是纯噪声。所以同一个 chunk 存两份：`text` 给检索链路，`content` 给拼 context。一句话：**两路召回、RRF 融合、rerank 精排，全链路只看 text；只有最终生成的时候，才把 content 里的原始信息展示给模型**。小表格的内联机制：元素流里放边界标记 `〔表格T0〕文本化内容〔/表格T0〕`，切块后 text 版剥标记、content 版把标记对替换回 HTML——标记只活在切块瞬间，两头都不污染。
- **图片走 VLM 生成描述**——描述是纯文本，天然进同一个 embedding 空间；原件落 `data/media/`，chunk 的 content 里只存文件名。命中图片块时来源面板直接回显原图（`GET /api/media/<文件名>`）。VLM 失败不阻塞入库：描述降级为占位符，11 张图里挂一张不影响剩下十张（离线管道的容错原则）。
- **rerank 只看 text**——表格/图片以文本化形态参与精排，三种模态归一到同一竞争空间。这就是多模态检索的口径：模态差异在入库时消化（解析→文本化），检索链路一行不改。

顺带一个**有意的不对称**：图片在来源面板回显原件，表格不回显。图片原件是文件，`<img src>` 指向受控的静态路由即可，不构成 HTML 注入面；表格的「原件」是 HTML 字符串，要可视就得走 `innerHTML` 渲染——而前端全程只用 `textContent`（改造① 的 XSS 纪律）。于是表格的 HTML 只回填给模型（换的是读数精度），用户在面板里看到的是文本化 preview。安全纪律与渲染需求的取舍，demo 选择保纪律。

schema 相应加三个字段（`chunk_type` / `content` / `page`），旧库自动检测重建。超长表格按行拆片这类扩展先不做——本语料最大表格 23 行、HTML 几 KB，VARCHAR 65535 远够；真遇到几百行的表再上。

### 改造⑥：接入钉钉机器人（Stream 模式，可选）

到这里 RAG 还活在浏览器里。这一步把它接进**聊天工具**：钉钉里直接 @机器人 提问，答案带着引用来源回到聊天窗口——`bot.py` 一个文件，检索/生成链路零改动。

**通道为什么选 Stream 模式**：钉钉机器人收消息有两种接法。Webhook 模式要求一个**公网可访问的 HTTPS 回调地址**——家庭宽带 NAT 后面就得内网穿透、域名、证书全套；Stream 模式是**出站 WebSocket**：本进程主动连钉钉服务器，消息从平台推下来，零公网 IP、零域名、零证书，家里常开的机器直接能跑。这是「接入聊天工具」成本最低的路径，也是选它做 demo 的原因。

```
钉钉服务器 ←—WebSocket（出站）—→ bot 线程（与 Flask 同进程，见下）
                                    │ conversation_id + 文本
                                    ├─ SQLite 取该会话最近 3 轮（服务端会话）
                                    ├─ 先发 AI 卡片占位（「执行中」）
                                    ├─ retrieve → build_context → 流式生成边收边写卡片（打字机）
                                    ├─ 本轮问答落库（来源/延迟/token = 使用日志）
                                    └─ ai_finish 定稿：答案 + [N] 来源脚注
```

三个设计点，每个都有对照：

- **会话状态从「前端持有」换成「服务端持有」**。改造② 里 Web 端的 history 由浏览器持有、随请求上送（无状态服务）；机器人没有「前端」，会话必须服务端存——SQLite 按 `conversation_id` 隔离（单聊/群聊天然分开），入史的是**原始问题**（不带参考资料，防多轮滚雪球，与 Web 端同口径）。这是聊天平台替你藏掉的另一半：现在两边都摊开过了。
- **先 ACK 再异步回答，回复用 AI 卡片打字机**。生成延迟中位 5s+、P95 可到 20s，而 SDK 的 `process` 同步等完会触发钉钉**超时重推**（官方 issue 实锤）——所以收到消息立刻返回 ACK，生成丢线程池异步做；另按 `message_id` 去重挡住仍可能到达的重推。回复不再是「等全生成完一次性蹦出」：先发一张「执行中」卡片占位，生成走**流式**（`messages.stream`）边收边往卡片写。打字机要**三要素齐活**（实测缺一不可）：首帧经 `ai_streaming` 把卡片置 INPUTING 态、后续帧走底层 `streaming()` 全量直发（~1s 节流）、终帧带 `isFinalize=true` 收掉流式会话——SDK 的 `ai_streaming` 永远不置 finished，缺终帧时卡片会挂在流式会话里、只渲染第一帧。另外**两枚卡片权限**都要在开放平台开（`Card.Instance.Write` 建卡 + `Card.Streaming.Write` 流写）；建卡失败是 SDK 静默失败（不抛异常、`card_instance_id` 留空），必须显式校验该字段、否则废卡会吞掉降级路径——卡片不可用时降级整条 markdown 回复。生成同时**关掉了思考块**（`thinking: disabled`）——语料数值问答不需要长思考，实测单次快 ~30%、思考 tokens 全省；token 用量从流的 `get_final_message()` 拿（在 with 块内，流式也能记账）。关思考后的质量抽查 4/4：两组财务数值、每股收益、锂价趋势、化学式拒答全对。
- **history 表就是使用日志**。每轮把问题、答案、命中来源、延迟、token 落库——「检索质量」坏例的排查、真实 query 分布的积累，都从这张表长出来。小范围落地最先该有的不是功能，是这张表。
- **一个 `__main__` 双模块坑**：`python demo.py` 运行时本模块名是 `__main__`，而 bot.py 里 `import demo` 会再加载一份**没跑过 main() 的裸副本**（单例全是 AttributeError——首轮实测就撞上了）。修法一行：起 bot 线程前 `sys.modules["demo"] = sys.modules["__main__"]`，把入口模块注册成 demo，bot 拿到的才是同一个正在跑的模块。入口脚本 + 被别的模块 import，两顶帽子戴在一个文件上时必踩。

工程上的一个约束决定了形态：**bot 是 Flask 同进程里的线程，不是独立进程**——Milvus Lite 单进程文件锁，两个进程各开一次库必挂；同进程线程则共享 `main()` 里接好线的单例，检索/生成代码一行不改。

启动（两个 env 都设才起线程，不设则行为与之前完全一致）：

```bash
set DINGTALK_CLIENT_ID=xxx        # 钉钉开放平台 → 应用 → 凭据与基础信息
set DINGTALK_CLIENT_SECRET=xxx
set ANTHROPIC_API_KEY=你的智谱key
python -X utf8 step4_app/demo.py  # Flask 照常起，控制台多一行 "[BOT] 钉钉机器人已启动"
```

钉钉侧一次性配置：注册团队 → [open-dev.dingtalk.com](https://open-dev.dingtalk.com) 创建应用 → 添加「机器人」能力 → 消息接收模式选 **Stream 模式**。**不发布也能用**（实测：未发布、未认证的个人团队，Stream 收发消息全部正常——文档里的「组织认证」要求挡的是正式发布流程，不是消息通道；管理员搜索应用名即可找到机器人开聊）。

边界（小范围信任圈的刻意取舍）：不做用户白名单和 token 熔断（群里都是熟人，配额风险可控，真要用再加十几行）；非文字消息（图片/文件）回复「暂时只支持文字提问」；多租户/权限隔离仍然没有——这已经是对话轮到「系统设计」题了，不是 demo 题。

### 跑起来

前提：智谱 Key 设成环境变量（本步不依赖 Ollama），然后 `python -X utf8 step4_app/demo.py`。首次启动自动创建空库 `data/mini_rag.db`；库里留着上次的数据则直接接着用（落库即持久化，重启不丢）。点「导入」选 `sample_reports/盐湖股份2024年报（精选页）.pdf`（PDF 分支会先跑多模态解析 + 11 张图逐张过 VLM，约半分钟）：

```
[OK]「盐湖股份2024年报（精选页）」+35 块（20文本 + 4表格 + 11图片，VLM 描述 11/11）
```

然后在右栏问「公司2024年赚了多少钱？」——来源面板先亮出来（Milvus 两路召回 → RRF 融合 → rerank 精排 → Top-3，即 LLM 回答里「根据[N]」的出处；`rrf` 是库内融合分、`score` 是精排分；条目带类型标注），紧接着答案开始流式往外吐：

```
本次检索来源（Milvus 两路召回：稠密向量 + BM25 → RRF 融合 → rerank 精排 → Top-3）：
  [1]（表格）rrf=0.0328 score=1.0 · 盐湖股份2024年报（精选页） p4
      表头：、2024年、2023年、本年比上年增减、2022年 营业收入（元）｜15,134,119,500.89｜21,578,504…
  [2]（表格）rrf=0.0317 score=1.0 · 盐湖股份2024年报（精选页） p5
  [3]（正文）rrf=0.0308 score=1.0 · 盐湖股份2024年报（精选页）

助手（流式）：
根据[1]的财务数据表格：
- 2024年营业收入：15,134,119,500.89 元（约151.34亿元），比上年下降 29.86%
- 2024年归属于上市公司股东的净利润：4,663,116,528.38 元（约46.63亿元），比上年下降 41.07%
```

看多模态在工作：`[1]` 是**表格块**——「主要会计数据」大表（15 行）解析成独立 chunk，检索时以文本化形态参与两路召回与精排，生成时 LLM 拿到的却是 HTML 原文（行列结构完整，按单元格读数），所以数字读得又准又全。`rrf` 的量纲也读得出来：单路命中 ≈ 1/(60+名次) ≈ 0.016，两路命中叠加到 0.030+——表格块 rrf 最高正是因为文本化版在稠密、稀疏两路都命中了。

再问一句「年报里那张饼状图展示了什么？各国占比是多少？」——这次 Top-3 里两块是**图片**：

```
本次检索来源（Milvus 两路召回：稠密向量 + BM25 → RRF 融合 → rerank 精排 → Top-3）：
  [1]（图片）rrf=0.0317 score=1.0 · 盐湖股份2024年报（精选页） p7
      图片描述：这是一个饼状图，展示了不同国家或地区的比例分布。图中列出了多个国家和
      地区，包括俄罗斯、白俄罗斯、加拿大、老挝、以色列、约旦和其他。
  [2]（正文）rrf=0.0318 score=1.0 · 盐湖股份2024年报（精选页）
      图8 2023年全球锂资源储量分布  图9 2023年全球锂资源产量分布
  [3]（图片）rrf=0.0318 score=1.0 · 盐湖股份2024年报（精选页） p10
      图片描述：这是一个饼状图……其中，智利以34%的比例位居第一，澳大利亚22%……

助手（流式）：
根据资料，盐湖股份2024年年报中出现了不止一张饼状图，以下分别说明：
一、第7页的饼状图 [1]——俄罗斯 33.6%、白俄罗斯 22.9%、加拿大 18.4%、老挝 16.4%、
   以色列 5.0%、约旦 3.0%、其他 0.7%，俄罗斯占比最高，占据主导地位。
二、第10页的饼状图 [3]——智利 34%、澳大利亚 22%、阿根廷 13%、中国 11%……
   前三位国家（智利、澳大利亚、阿根廷）合计约69%，占据较大份额。
三、另有图8、图9两张饼状图 [2]——资料中图片内容描述不完整，未给出各国具体占比数字。
```

两个细节值得看：**VLM 描述里带着图上标注的真实百分比**（俄罗斯 33.6% 那组）——描述质量直接决定图片检索与回答的上限，glm-4v 能把图例数字读出来，LLM 就能引成数；`[2]` 是图片标题所在的**正文块**（图8/图9 的图题文字），与图片块互补——图题告诉模型「这是什么图」，VLM 描述给「图里有什么」。命中图片时，来源面板下方还会经 `/api/media/` 直接回显原图。

线路上传的是一帧一帧的 SSE（另一次提问的实测帧节选）：

```
event: delta
data: {"text": "资料"}

event: delta
data: {"text": "中"}

event: delta
data: {"text": "未"}

...（几十帧）

event: done
data: {}
```

顺手看两个边界行为（都是实测）：

- **防幻觉在工作**：问「公司2025年打算给股东分红多少？」——语料里没有分红信息，检索照样返回「最不差的」Top-3（精排分全是 1.0：Cross-Encoder 只会排「哪个更像答案」，证不了「没有」），但模型守住 system 约束如实拒答、还列举了资料里实际有什么：「资料中未提及……仅包含主要会计数据（营业收入、净利润、每股收益等）与成本构成数据」。检索送不存在的答案送不上来，LLM 也不编——这正是 step3 防幻觉两道关的产品化表现。
- **空库提问**：`POST /api/chat` 返回 `400 {"error": "向量库为空，请先在左侧导入文档"}`，前端显示成气泡里的 ⚠️ 提示。

这就是一个「能用」的 RAG 产品了：浏览器打开、选文档、提问、看答案一个字一个字出来、每条答案都能追溯到出自哪份年报的哪个 chunk。整个过程没碰过命令行（除了第一次启动）。

## 3. 评测：让「检索质量」从感觉变成数字

§2 结尾说「这是一个『能用』的 RAG 产品了」——但「能用」是演示出来的：§2 挑的三个问题恰好是链路表现最好的形态。demo 的本能是给你看最好的 case；评测的本事是把「感觉不错」变成可重复的数字。这一节给 step4 配一套小而全的评测设施：一份分层评测集（`evalset.py`）+ 一个判分脚本（`eval.py`）。

一次评测 = 给系统一个输入，用一段判分逻辑检查输出，看成没成。批量、分层、可重复地做这件事，就是评测集 + 判分器 + 指标三件套。

### 评测集怎么建：每条 case 的四要素

`evalset.py` 里 15 条 case，每条把「输入 / 初始状态 / 成功标准 / 参考解答」四要素写全：

```python
{
    "id": "C01", "layer": "常规", "tag": "表格",
    "question": "公司2024年营业收入和归母净利润分别是多少？",   # 输入
    "expect": [{"type": "table", "page": 4}],                # 成功标准①：检索层标准出处
    "assert_groups": [["15,134,119,500", "151.34"],          # 成功标准②：生成层关键词断言
                      ["4,663,116,528", "46.63"]],           #   每组任一命中、全部组过才算对
    "note": "两组数值（营收 + 净利）都要对",                   # 参考解答（人读的）
}
```

初始状态全 case 共享：同一份语料库（35 块精选页）+ 同一套检索参数。分两层判分，是因为 RAG 是两道工序——**检索层**判「标准出处进没进 Top-3」（表格/图片块按 类型+页码 锚定，正文块没有页码、用关键词锚定）；**生成层**判答案本身（财务数值题能写成断言的绝不靠肉眼）。

分层是该做的题里再分难度，外加不该做的题：

| 分层 | 条数 | 形态 |
|---|---|---|
| 常规 | 8 | 语料里有、问法直白——应该拿分的基本盘（表格 5 / 正文 2 / 正文+图片 1） |
| 边界 | 5 | 短查询、跨块聚合、图片定性、**措辞转换**、**答案埋在行政文本**——检索或生成被加压 |
| 异常 | 2 | **不该做的题**：2025 经营计划、氯化钾化学式——语料里没有，期望拒答。化学式那题最狠：模型的世界知识里有 KCl，考的是「只能根据参考资料回答」的约束力 |

> **评测集自己的标签也会错。** 第一版把「董事长是谁」「分红方案」都标成了语料外异常题；逐 case 核对语料后发现两处都标反了——p3 表格里写着「法定代表人：侯昭飞」，重要提示里写着「公司计划不派发现金红利」。前者改成边界题（措辞转换，问董事长、答法定代表人）；后者更是从「不该做」变成了「该做但答不出」（见下节的 B05）。评测集建成 ≠ 评测集正确——每条「语料外」假设都要拿语料逐 case 核对过再定标签。

### 跑起来：判分与指标

前提同 demo.py（Key + 库里已导入精选页 PDF），每条 case 独立跑 3 次完整链路（生成是概率性的，跑一次说明不了什么）：

```bash
python -X utf8 step4_app/eval.py            # 或 --runs 5 调多次试验的次数
```

实测输出（真实数字，非示意）：

```

  命中@3  30/39（76.9%） · Top-1  27/39（69.2%）
  分层（按 run 计）：常规 21/24 · 边界 9/15

  该做的题   答对 31/39（79.5%）
  不该做的题 拒绝 6/6（100.0%）

```

指标怎么读，一条一条说：

- **命中@3 / Top-1（检索层）**：标准出处进 Top-3 算命中、排第一算 Top-1。该做 13 题 × 3 run = 39 次里，76.9% 命中。分层看更诚实：常规 87.5% vs 边界 60%——加压形态确实更难，这正是分层的目的（一把平均数会把「基本盘稳、加压弱」平均成「还行」）。
- **答对率 / 拒绝率（生成层）**：该做的题 79.5% 答对（断言过 = 数值/关键词全对）；不该做的题 6/6 全拒——连化学式 KCl 都没漏，「只能根据参考资料回答」的约束在这套评测里守住了。
- **pass@3 vs pass^3**：做成一次就够（结果可自动验证、挑能用的那份）vs 三次全对（面向用户、每次都得靠得住）。C08 是两者差异的活例子：3 次里 1 次读全了占比数字，pass@3 算过、pass^3 不算——11/13 vs 10/13 的那 1 条差距就是它。
- **延迟看中位数也看 P95**：生成中位 5.4s、P95 却到 25.6s——模型思考的长尾。单次慢不说明什么，5% 的请求慢才是要优化的对象；只报平均数会把长尾藏掉。
- **成本**：45 次生成 8.4 万 token、均 1,870/次——评测顺手把账也记了，换模型/换参数时这套账就是对照基线。
- **过程指标**：rerank 降级 0/45（rerank API 全程健康）。降级是静默发生的（失败回退融合顺序），不记就看不见。

### 各环节拆开看：四个象限定位问题

成功率上不去时，按环节拆开看，才分得清是检索没捞到还是生成没答好。两层判分交叉出的四个象限，这套评测里各有真实样本对号入座：

| 检索 | 生成 | 诊断 | 本套里的实例 |
|---|---|---|---|
| ✓ | ✓ | 链路健康 | 9/13 条（C01-C05、C07、B01、B03、B04 检索生成双全绿） |
| ✓ | ✗ | 检索送到了，生成没答好——读数/推理问题 | **C08**：检索稳定 Top-1，但占比数字 3 次只读全 1 次（多模态数值读数不稳定） |
| ✗ | ✓ | 答对了，但不是「检索送过去的答案」——细看两种可能 | **C06**（见下） |
| ✗ | ✗ | 检索层锅：先修召回，生成侧无从发力 | **B02 / B05**（见下） |

两个象限值得展开——它们是这套评测最值钱的发现：

**C06（检索✗ 生成✓）**：问「进口依存度多少」，含 67% 的正文块没进 Top-3，模型却 3/3 答对。看答案才知道怎么回事——它明说「资料中并未直接给出这一数字」，然后用检索到的**产量 620.5 万吨**（[1]）和**表观消费量 1872 万吨**（[3]）现场推算：(1872−620.5)÷1872 ≈ **67%**。数字对，推导也对，但和标准答案只是殊途同归。这个象限提醒两件事：一是**答案对 ≠ 链路对**，若哪天语料改了数、推算路径还在，就会稳定地答错；二是**代码断言只验结果不验过程**——判分器的分工本来就是「能代码判的用代码，代码判不了的（过程、表述质量）用模型判或人工抽检」，这里恰好是断言的能力边界。

**B05（检索✗ 生成✗，但最值得琢磨）**：问「2024 年度分红方案」，**答案就在库里**——重要提示里白纸黑字「公司计划不派发现金红利，不送红股，不以公积金转增股本」。但「重要提示」这类行政文本与「分红」查询的语义距离太远，两路召回 + 精排都没把它送进 Top-3；LLM 拿着三块不相关的资料，守着 system 约束如实回答「资料中未提及」。step3 讲过防幻觉两道关——检索送相关 + LLM 守规矩；这个 case 展示的是第一道关失守时，第二道关会把「没送到」当「没有」：**拒答 ≠ 安全，也可能是召回缺口的假阴性**。修法方向（query 改写、把行政文本块单独建通道）超出本 step，但评测的职责到「把问题定位到环节」为止，已经完成。

### 边界与扩展

- **断言判分只验结果**：C06 那种「推算对了」与「检索送到答对了」在指标里无法区分——要验过程得上模型判分（用模型验证模型，引入新的不确定性，本 demo 不做）或人工抽检。
- **15 条 × 3 run 是教学规模**：够把问题定位到环节，不够做统计置信；pass^3 的 N=3 也只是示意。
- **留作扩展**：评测设施建好后，最自然的下一步是**环节消融**——加 `--no-rerank` / 单路召回开关跑对比，让「rerank 值不值、BM25 那路贡献多少」也变成数字；再往后是扩评测集、换语料验泛化。

## 4. 四步走完

回头看这四步：

1. **[基础件](../step1_basics/README.md)**：分块（递归切分保语义边界）+ 向量化（Embedding，余弦相似度找语义接近）。
2. **[向量库](../step2_index/README.md)**：JSON + numpy 存 chunk 和向量，从零实现检索。
3. **[完整 RAG](../step3_rag/README.md)**：混合检索（向量 + BM25 两路召回、RRF 融合、rerank 精排）+ 拼 context + system 约束 + LLM 生成，闭环 + 防幻觉两道关。
4. **聊天界面 + 工程底座 + 多模态 + 评测**（本 step）：Flask 手写 Web 层，SSE 流式 + 文档上传；检索底座从手搓三件套换成 Milvus Lite；PDF 直接入库，正文/表格/图片三种模态同一检索空间；一套分层评测集让检索质量从感觉变成数字（§3）。
   
一套朴素 RAG 的骨架就这么搭起来了。前三步每个零件都最简、都看得见——embedding 是一次 HTTP 调用、分块是递归切分隔符、向量库是余弦点积、检索是召回 + 精排、生成是拼 prompt 喂 LLM。第四步在看清每个零件内部是什么之后，把存储与检索底座换成工业件（Milvus）、把语料从纯文本升级到多模态 PDF、外面加上 6 个路由 + 一段 SSE 的 Web 层——先没有黑盒，再心安理得地用黑盒。

最后一块拼图——**评测**——已经在本步落地（§3）：15 条分层 case、两层判分、四个维度的指标，检索质量从感觉变成了数字，还顺手抓出了「答案在库里却假拒答」这类演示永远看不到的问题。带上这套度量再往前走（扩评测集、环节消融、换更强的检索底座），每一步「变好」都有数字作证。
