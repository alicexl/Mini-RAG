# Step 3 讲稿：本地向量库 —— 存起来，检索出来

---

## 一、为什么需要向量库

[Step 2](../step2_chunking/讲稿.md) 把长文档切成了 chunk，[Step 1](../step1_embedding/讲稿.md) 把每个 chunk 变成了向量。现在手头有一堆 `(chunk 文本, 向量)` 的配对。RAG 查询时要做的，就是**把用户的问题也变成向量，然后在这一堆里找出最相似的几个 chunk**。

这堆 `(chunk, 向量)` 怎么管？总不能每次查询都重新切一遍文档、重新 embed 一遍——那又慢又贵。所以需要一个**向量库（vector store）**把它管起来，干两件事：

- **存**：chunks 和它们的向量持久化下来，下次查询直接复用，不重新 embed
- **检索**：给一个查询向量，返回最相似的 Top-K 个 chunk

这一章就从零搭一个最小的向量库——**原文用 JSON 存，向量用 numpy 存，检索用余弦相似度**。不依赖任何向量数据库，把"检索到底在做什么"彻底摊开。

---

## 二、存什么：原文 + 向量 + 元信息

向量库本质是**三组并列**的数据：

- **原文（chunks）**：检索回来要喂给 LLM 的文本
- **向量**：用来算相似度的那串数字
- **元信息（metadata）**：每块的来源、标题等——检索命中后，光有文本不够，还要知道这段出自哪份文档

三组的"形状"不一样，存法也各用各的：

- 向量是**数值矩阵**——N 个 chunk，每个 1024 维，组成一个 `N × 1024` 的二维数组。用 numpy 存成 `embeddings.npy`（二进制），存取快、占空间小。
- 原文是**文本**——存成 `chunks.json`，人能直接读、方便调试（`cat` 一下就能看到第几条 chunk 是什么）。
- 元信息是**结构化的小字典**——存成 `metadata.json`，和 `chunks` 一一对应（第 i 条记第 i 块的来源）。

三个文件放在同一个 `data/` 目录下——这是真实 RAG 项目常见的存储布局：一个语料一个目录，目录里分文件装原文、向量、元信息。

**入库（`add`）是同步追加**：原文、元信息直接 append 到对应列表；新向量用 `np.vstack` **拼在向量矩阵底部**（行数相加、列数不变）。关键约定：**第 i 行永远是第 i 个 chunk 的向量**——检索找到最像的行号，就从 `chunks` 取同一位置的原文。

`VectorStore` 的存盘就这么三行：

```python
def save(self, data_dir):
    data_dir = Path(data_dir)
    data_dir.mkdir(parents=True, exist_ok=True)
    (data_dir / "chunks.json").write_text(
        json.dumps(self.chunks, ensure_ascii=False, indent=2), encoding="utf-8")    # 原文
    np.save(data_dir / "embeddings.npy", self.vectors)                               # 向量矩阵
    (data_dir / "metadata.json").write_text(
        json.dumps(self.metadata, ensure_ascii=False, indent=2), encoding="utf-8")   # 元信息
```

读回来（`load`）就是反过来：两个 JSON 解析回 `list[str]` / `list[dict]`，`.npy` 读成 numpy 数组。一存一读，向量库就落了盘，进程关掉再开也不丢。

> 为什么不用一个文件装？可以（比如把向量也塞进 JSON），但 1024 维浮点数写成 JSON 文本会膨胀好几倍、读写都慢。向量是规整的数值矩阵，天生适合 numpy 的二进制格式；原文是变长文本，天生适合 JSON。各用各的格式，是顺理成章的事。

## 三、检索：余弦相似度 + Top-K

检索拆成两步：**算分** + **排序取前 K**。

### 算分：查询向量 vs 每个 chunk 向量

把查询 embed 成一个向量 `q`，和库里的每个 chunk 向量算余弦相似度，得到 N 个分数。[Step 1](../step1_embedding/讲稿.md) 的余弦是两个向量逐元素算的（标量循环）：

```python
dot = sum(x * y for x, y in zip(a, b))
return dot / (norm_a * norm_b)
```

但检索要算的是**一个查询 vs 所有 N 个 chunk**，不是一对。逐对循环算 N 次太慢——这里用**矩阵化**一次性算完。

关键观察：**余弦相似度 = 归一化后的点积**。先把库里的向量矩阵按行归一化（每行除以自己的长度），查询向量也归一化，然后一次矩阵乘：

```python
def _cosine_to_all(self, q):
    q_norm = q / (np.linalg.norm(q) + 1e-8)                          # 查询向量归一化 -> (dim,)
    v_norm = self.vectors / (np.linalg.norm(self.vectors, axis=1,    # 所有 chunk 向量按行归一化
                                             keepdims=True) + 1e-8)  # -> (N, dim)
    return v_norm @ q_norm        # (N, dim) @ (dim,) -> (N,)，一次得到 N 个相似度
```

`v_norm @ q_norm` 这一步，矩阵乘法的物理含义就是"`q` 和每一行的点积"——而两边都归一化过了，点积即余弦。numpy 底层走 BLAS，比 Python 循环快得多。这就是把 Step 1 的"两个向量算余弦"推广到"一个向量 vs 一群向量"。

### 排序取前 K

拿到 N 个相似度后，降序排个序、取前 K 个，就是 Top-K：

```python
sims = self._cosine_to_all(q)        # (N,)
order = np.argsort(-sims)[:top_k]    # argsort 默认升序，加个负号变降序，取前 K
```

`np.argsort` 返回的是**下标**而非值——正好，我们要的就是"第几个 chunk 最相似"，用下标去 `self.chunks` 里取原文。

## 四、动手：完整检索链路

把前三步串起来，就是一条完整的 RAG 检索链路：

```
文档 → 切块(step2) → embed(step1) → 入库(step3) → 查询embed → 余弦Top-K → 返回chunk
```

跑 demo（`PYTHONUTF8=1 python step3_index/demo.py`），输入是一段约 670 字的盐湖股份年报文本，切成 chunk_size=200 的块：

```
[1] 切块 + 向量化 + 入库
    文档 671 字 → 切成 5 块（chunk_size=200）
    入库 5 个 chunk，向量矩阵 shape=(5, 1024)，元信息 5 条

[2] 持久化：save → load（data/ 目录：chunks.json + embeddings.npy + metadata.json）
    存盘 data/：chunks.json（原文 5 条）+ embeddings.npy（向量 (5, 1024)）+ metadata.json（元信息 5 条）
    重载：5 个 chunk，向量矩阵 (5, 1024)，元信息 5 条（与原库一致）
```

然后三个查询——**措辞故意和原文不一样**，看语义检索（而非字面命中）的效果：

```
查询: 公司2024年赚了多少钱？        （原文讲"营业收入/净利润"）
  [0] sim=0.362  [盐湖股份2024年年报（示例）] 盐湖股份2024年实现营业收入150亿元…归母净利润45亿元…
  [1] sim=0.325  [盐湖股份2024年年报（示例）] 钾肥是公司的传统主业…
  [2] sim=0.300  [盐湖股份2024年年报（示例）] 碳酸锂是公司的第二增长曲线…

查询: 锂业务的产能有多大？          （原文讲"碳酸锂产量3.5万吨"）
  [2] sim=0.538  [盐湖股份2024年年报（示例）] 碳酸锂是公司的第二增长曲线。2024年碳酸锂产量达到3.5万吨…
  [4] sim=0.473  [盐湖股份2024年年报（示例）] 展望未来，公司计划继续扩大碳酸锂产能，目标三年内将产能提升至5万吨…
  [3] sim=0.375  [盐湖股份2024年年报（示例）] 碳酸锂价格在2024年持续下跌…

查询: 钾肥是公司的主要业务吗？      （原文讲"钾肥是传统主业/压舱石"）
  [1] sim=0.698  [盐湖股份2024年年报（示例）] 钾肥是公司的传统主业…钾肥业务贡献了公司过半的营业收入和利润…
  [4] sim=0.460  [盐湖股份2024年年报（示例）] 展望未来…钾肥业务有望受益于国际农产品价格上涨…
  [2] sim=0.392  [盐湖股份2024年年报（示例）] 碳酸锂是公司的第二增长曲线…
```

### 怎么读这组结果

- **三个查询的 Top-1 都命中了对应主题**（赚钱→业绩段、锂产能→碳酸锂段、钾肥→钾肥段）。查询词和原文措辞并不重合——"赚钱"vs"营业收入"、"锂业务"vs"碳酸锂"——靠的是 [Step 1](../step1_embedding/讲稿.md) 的语义向量，不是字面匹配。这就是稠密检索的价值。
- **每行方括号里是元信息里的来源**——命中后自动带上出处。这就是 metadata 的用武之地：库里几十份文档时，检索回来不仅知道"最相关"，还知道"出自哪"，RAG 里可追溯、可引用（本例五块同源，所以都一样）。
- **相似度的绝对值不高，但排序是对的**。"赚了多少钱"的 Top-1 才 0.362，照理不算"很相似"。这正好印证了 Step 1 那句话——**RAG 检索用 Top-K 而不是硬阈值**：如果卡个 0.5 的阈值，这个查询就什么都召回不回来，可它的 Top-1 明明是对的。短查询对长 chunk 的余弦天生偏低，看排序、别看绝对值。
- **查询越具体、字面越接近，相似度越高**。"钾肥是主要业务吗"0.698 远高于"赚了多少钱"0.362——前者连字面都和钾肥段高度重合，后者只是泛泛地问"赚钱"。同样是 Top-1，分数可以差很多，所以阈值根本定不了一个万能值。

## 五、朴素向量库的边界

这个向量库是教学版，刻意做到最简——能看清"存 + 检索"在做什么。但它有两个层面的局限，生产级 RAG 都要解决。

### 检索算法的边界：线性扫描扛不住大规模

`search` 每次查询都要算 `q` 和**所有** N 个 chunk 的相似度——复杂度 O(N)。库小（几百几千 chunk）没感觉，但真实场景动辄百万级 chunk，每次查询都全量算一遍就慢得不可接受。

生产级解法是**近似最近邻（ANN）**索引：FAISS、hnswlib、Milvus 这类工具用图或聚类的结构，做到**亚线性**检索（不用扫全部，也能以极高概率找到真 Top-K）。代价是有一点精度损失、构建索引要时间，但换来的是海量向量下的可用性。

### 检索范式的边界：只有稠密，缺稀疏

这个库只做**稠密检索**——纯靠 embedding 向量的语义相似度。但语义相似度有盲区（Step 1 讲过）：它擅长"主题相近"，弱于"精确字面"和"逻辑关系"。比如用户搜一个专有名词、型号、人名，embedding 可能把它们和语义相近但字面不同的内容混在一起。

传统检索（TF-IDF / BM25）走的是另一条路——**稀疏表示**：把文本看成词频向量，靠**字面命中**打分（"营收"这个查询词在哪些文档出现、出现几次、区分度高不高），再用**倒排索引**做到 O(1) 查词。它精确匹配强、可解释，但理解不了"营收"和"营业收入"是一回事。

一句话区分：**稀疏是"字面指纹"，稠密是"语义指纹"**。

|  | 稀疏（TF-IDF / BM25） | 稠密（Embedding） |
|---|---|---|
| **怎么判断相关** | 查询词字面命中，按词频/区分度打分 | 向量余弦相似度 |
| **"营收" vs "营业收入"** | 不同词，关联不了 | 语义相近，自然关联 |
| **索引结构** | 倒排索引（O(1) 查词） | 向量索引（线性扫描或 ANN） |
| **擅长** | 精确匹配、专有名词、可控可解释 | 理解语义、容错、跨表述 |

它们不是谁替代谁——生产级 RAG 通常**两者都用**（混合检索），稠密负责"语义相关"、稀疏负责"字面精确"，把两路结果合并再喂给 LLM。本项目只做稠密这一支（朴素 RAG），混合检索、rerank 这些工程化能力留给生产级 RAG 系统。

> 这一章的向量库 = JSON 存原文 + numpy 存向量 + JSON 存元信息 + 余弦线性扫描。它把 RAG 检索的骨架讲透了：**查询向量和每个 chunk 向量算余弦，排序取 Top-K**。生产向量数据库（FAISS / Milvus / Chroma）在这套骨架上加了 ANN 索引、混合检索、分布式、增量更新——但"算相似度取 Top-K"这个内核没变。
