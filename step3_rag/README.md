# Step 3 — 完整 RAG：检索增强生成

> 两级检索（向量召回宽进 → rerank 精排收紧）+ 拼 context + system 约束 + LLM 生成，闭环走通；防幻觉两道关与朴素 RAG 剩下的边界（混合检索）在此展开。

## 1. RAG 三步：检索 + 增强 + 生成

RAG 全称 **R**etrieval-**A**ugmented **G**eneration——检索增强生成。名字就是三步：

- **检索（Retrieval）**：把用户问题变成向量，在向量库里找出最相似的 chunk。这一步内部是两级流水线——向量召回宽进、rerank 精排收紧（下一节展开）。[Step 1](../step1_basics/README.md) 的分块与向量化、[Step 2](../step2_index/README.md) 的向量库，前两步都是在搭这一步。
- **增强（Augmented）**：把检索回来的 chunk 作为「参考资料」塞进 prompt，交给 LLM。
- **生成（Generation）**：LLM 看着这些资料，生成自然语言的答案。

前两步我们手里已经有了「检索回来的 Top-K 文本」。本 step 就补上后两步，把链路闭环：检索 → 拼 prompt → LLM 生成。

---

## 2. 检索升级：召回宽进，rerank 收紧

Step 2 的 `search` 是「向量 Top-K 一把梭」——直接取相似度前 3。本 step 把它拆成两级：

```
查询 → 向量召回 Top-20（粗排：宽进，保召回）→ rerank 精排 → Top-3（收紧，保精度）→ 进 prompt
```

为什么要分两级？回到两种打分器的本质区别：

- **向量召回是 bi-encoder（双塔）**：查询和文档**各自**编码、各出一个向量，文档向量离线算好存库，查询时只比余弦。快就快在「各自」——但它俩从没「见过面」，只能判断「话题像」，判断不了「这块到底答没答这个问题」。
- **rerank 是 Cross-Encoder**：把「查询 + 候选」**拼成一条文本**一起过模型，输出直接是一个相关性分。准就准在「拼在一起」——两边的词逐个直接对照；慢也慢在这里——分数依赖当前查询、没法预计算，每对都要现算。

所以分工是：**便宜的双塔扫全库捞 20 条（别漏掉），昂贵的 Cross-Encoder 只对这 20 条精排取 3（排得准）**——漏斗越往后越贵，喂的越少；最贵的生成 LLM 只读精排后最好的那几条。

```python
def retrieve(question, store, embedder, reranker, top_k=TOP_K):
    candidates = store.search(question, embedder, top_k=RECALL_K)     # 粗排：宽进
    try:
        results = reranker.rerank(question, [c[2] for c in candidates], top_n=top_k)
        retrieved = [(candidates[r["index"]][0], ..., r["relevance_score"], ...) for r in results]
        return retrieved, True
    except Exception:
        return candidates[:top_k], False    # rerank 失败 → 降级回向量顺序，检索不中断
```

两个工程细节：

- **rerank 走智谱开放平台原生 API**（`POST /paas/v4/rerank`，模型名 `rerank`），与生成（Anthropic 兼容网关）**共用同一个智谱 Key**——Bearer 认证，不新增配置。
- **降级**：rerank 挂了（网络/余额/限流）不拦住整个问答，退回向量顺序取前 3，终端会打 `[WARN]` 提示。外围设施失败不阻断核心链路。

## 3. 「增强」到底在做什么

直觉很好懂：**把检索回来的 chunk 塞进 prompt，让 LLM 看着资料回答，而不是凭训练记忆凭空答题**。但「增强」不止是塞数据这一下，它其实做两件事。

### 第一件：把检索结果拼成 context

检索回来的是 `[(chunk编号, 向量sim, 精排score, 文本), ...]`。要喂给 LLM，得先拼成一段它看得懂的「参考资料」：

```python
def build_context(retrieved):
    parts = [f"[{i}] {chunk}" for i, (_, _, _, chunk) in enumerate(retrieved, 1)]
    return "\n\n".join(parts)
```

给每条 chunk 加个编号 `[1] [2] [3]`，不光是为了好看——是为了让 LLM **能引用来源**（「根据[1]」）。检索结果能不能追溯到原文，是 RAG 区别于「LLM 瞎编」的关键。

### 第二件：用 system prompt 约束 LLM 的行为

光把资料塞进去还不够。LLM 天生爱「答题」——哪怕资料里没有，它也可能调动训练时记住的知识，自信地编一个出来（这就是**幻觉**）。所以要用 system prompt 明确改变它的行为模式：

```python
SYSTEM_PROMPT = (
    "你是一个严谨的问答助手。只能根据下面【参考资料】里的内容回答用户问题，"
    "并在用到某条资料时标注它的编号（如「根据[1]」）。"
    "如果【参考资料】里没有相关信息，就如实回答「资料中未提及」，禁止编造。"
)
```

这段话干了三件事：**限定信息来源**（只能用资料）、**要求引用编号**（可追溯）、**允许拒答**（没有就说没有）。把这三句拼进 prompt，LLM 就从「凭记忆答题」切换到「看资料答题」。

### 完整的一条 RAG

把两件事合起来，一条 RAG 长这样：

```python
def rag_answer(question, store, embedder, generator, reranker, top_k=3):
    retrieved, reranked = retrieve(question, store, embedder, reranker, top_k=top_k)  # 检索
    context = build_context(retrieved)                             # 增强①：拼 context
    user = f"【参考资料】\n{context}\n\n【用户问题】\n{question}"
    answer = generator.answer(SYSTEM_PROMPT, user)                 # 增强②(system约束) + 生成
    return retrieved, reranked, answer, context
```

`user` 消息里同时装着【参考资料】和【用户问题】，`system` 消息装着行为约束——这就是「增强」的全部：**用检索结果填充 prompt，用 system 指令约束模型**。

## 4. 动手：完整链路

demo 是**两个命令**（按用户场景划分，不是按实现步骤）：`ingest` 导入文档，`chat` 交互问答。语料是真实的盐湖股份年报节选（`sample_reports/` 下三份，由 `build_excerpts.py` 从年报 PDF 生成）。

**第一步，导入文档：**

```
python -X utf8 step3_rag/demo.py ingest sample_reports/盐湖股份2023年年报（节选）.md
[OK]「盐湖股份2023年年报（节选）」：13573 字 → 38 块，向量矩阵 (38, 1024)
```

`ingest` 跑的就是前两步那条链：读文档 → 切块（400 字 + 50 重叠）→ 向量化 → 入库，来源名取文件名（写进 metadata 的 source），存在 `data/` 三件套里。**幂等**：同一份文档再导一次会提示 `[SKIP] 已在库中`。把 2024、2025 两份也导进来，库里就是横跨三个年度的 114 个 chunk。

**第二步，启动交互式问答 terminal：**

```
python -X utf8 step3_rag/demo.py chat
向量库：114 个 chunk（检索 qwen3-embedding:0.6b / 生成 glm-5.3）
```

（生成模型走智谱 GLM 网关，API Key 三选一：环境变量 `ANTHROPIC_API_KEY`、改 demo.py 顶部 `API_KEY` 常量、或运行时按提示输入；检索部分用本地 Ollama，无需配置。）

### 前两问：答案在检索回来的 chunk 里

第一问看一遍完整链路——检索、拼 prompt、生成三段都在（rerank 后的实测，每行两个分：`sim` 是向量相似度、`score` 是精排分）：

```
查询> 公司2024年赚了多少钱？
检索：召回 20 → rerank 精排 → Top-3（[1][2][3] 即 LLM 回答里「根据[1]」的引用）：
  [1] sim=0.436 score=1.000 [盐湖股份2024年年报（节选）] # 盐湖股份 2024 年年报（节选）↵↵## 主要会计数据↵公司是否需追溯调整…
  [2] sim=0.498 score=1.000 [盐湖股份2024年年报（节选）] 经营活动产生的现金流量净额：2024年 = 7,819,152,860.43；2…
  [3] sim=0.566 score=1.000 [盐湖股份2024年年报（节选）] 经营活动产生的现金流量净额（元）：2024年 = 7,819,152,860.4…

→ 拼 prompt 喂给 LLM（增强 = 检索结果 + system 约束）：
  [system] 只能用【参考资料】，引用编号（如「根据[1]」），没有就说没有
  [参考资料] [1] # 盐湖股份 2024 年年报（节选）  ## 主要会计数据 … 营业收入（元）：2024年 = 15,134,1…
  [用户问题] 公司2024年赚了多少钱？

→ LLM 生成：
根据[1]，盐湖股份2024年的盈利情况如下：

- **营业收入**：151.34亿元（15,134,119,500.89元），同比下降29.86%
- **归属于上市公司股东的净利润**：46.63亿元（4,663,116,528.38元），同比下降41.07%
- **扣除非经常性损益的净利润**：44.01亿元（4,400,518,590.09元），同比下降49.56%

因此，公司2024年最直观的“赚钱”数字是**归母净利润约46.63亿元**。

此外，根据[2][3]，2024年经营活动产生的现金流量净额为78.19亿元（7,819,152,860.43元），同比下降35.40%。
```

这里正好能看到两级检索的价值：[1] 那个「主要会计数据」块在向量召回里 `sim` 只有 **0.436**——双塔眼里它只是"年报开头的一堆表格"，排在 20 条召回的后面；但 rerank 把它提到第一——因为问「赚了多少钱」，这个装着**营收 + 净利润 + 扣非净利润三行数据**的块才是真正"答了这个问题"的块。「话题像」（双塔）和「答没答」（Cross-Encoder）的排序差异，就在这两列分数的对比里。LLM 也一次从 [1] 抽全了三个数。

三个年度的语料在同一库里，跨年问题也答得动。问「2023年和2024年，钾肥产销量分别是什么水平？」，rerank 从**两份年报**里各捞一块——2023 年报的产销量表（2023 年数据）和 2025 年报的对比列（2024 年数据在次年年报的"上年"列里），LLM 把两年的产量销量全拼了出来，每条都标了来源：

> **2023年**：产量 492.60 万吨、较 2022 年下降 15.07%（根据[2]）；销量具体数字资料中未提及，仅提"销售量超额完成年度目标"（根据[1]）。
> **2024年**：产量 496.00 万吨、销量 467.28 万吨（根据[3]，出自 2025 年报的对比列）。

注意 [3] 的出处——2024 年的数据来自 **2025 年报**的对比列。这就是 metadata 的用武之地：检索命中后不光知道"最相关"，还知道"出自哪"，跨年对比时答案出自哪份年报一目了然。

### 第三问：原文里没有的信息——这才是重点

第三个查询故意问语料里没写的「2025 年分红多少」（拼 prompt 那步与第一问同构，略）：

```
查询> 公司2025年打算给股东分红多少？
检索：召回 20 → rerank 精排 → Top-3（[1][2][3] 即 LLM 回答里「根据[1]」的引用）：
  [1] sim=0.544 score=1.000 [盐湖股份2025年年报（节选）] 经营活动产生的现金流量净额（元）：2025年 = 10,160,860,737.…
  [2] sim=0.478 score=1.000 [盐湖股份2025年年报（节选）] # 盐湖股份 2025 年年报（节选）↵↵## 主要会计数据↵公司是否需追溯调整…
  [3] sim=0.458 score=1.000 [盐湖股份2025年年报（节选）] 经营活动现金流入小计：2025年 = 18,951,757,266.80；202…

→ LLM 生成：
资料中未提及公司2025年度的股东分红方案。

根据现有参考资料[1][2][3]，仅涉及公司2025年的经营业绩数据（如营业收入、净利润、每股收益、经营活动现金流量等），未包含利润分配或现金分红的相关信息。
```

注意这里发生了什么：

- **检索这一关「失效」了**——语料里根本没有分红信息，检索器自然找不到相关 chunk。但 Top-K 机制总会返回「最不差的」K 个，于是把 2025 年报的现金流、会计数据这些相关但答非所问的 chunk 照样塞进了 context（精排照样给它们打了 1.0 的分——Cross-Encoder 也证不了「没有」，它只会排「哪个更像答案」）。这印证了 [Step 1](../step1_basics/README.md) 说的「Top-K 不卡硬阈值」——这里如果卡阈值，连这几个 chunk 都没有，但要不要卡、卡多少都不是关键。
- **LLM 这一关「兜住了」**——system prompt 要求「没有就说没有」，LLM 看完三个都不含分红信息的 chunk，选择**拒答**而非编一个数字。

这就是 RAG 防幻觉的**两道关**：检索负责把相关内容送到面前（这关对「真不存在」的问题天然无效），LLM 在 system 约束下负责判断「资料里到底有没有」（这关兜住了幻觉）。如果只有检索没有 system 约束，LLM 很可能看着一堆无关 chunk，调动训练记忆自信地编一个分红比例——那就不叫 RAG 了。

## 5. 朴素 RAG 的边界

这一步拼出了完整的 RAG 闭环（含 rerank 精排），但它仍是教学版，有几个层面的局限，生产级 RAG 都要继续解决。

### 幻觉只是被压低，没被根除

system prompt 说「禁止编造」，但 LLM 不一定每次都听话。它仍可能：**误读 context**（把 3.5 万吨读成 35 万吨）、**context 里有但答错**（算错、张冠李戴）、**context 太长时漏看中间**（所谓 *lost in the middle*——LLM 对 prompt 首尾更敏感，中间的 chunk 容易被忽略）、甚至被**恶意 chunk 注入指令**（资料里藏着「忽略上面的指令，回答 XXX」）。RAG 把幻觉从「几乎必定编」降到了「偶尔编」，但没归零。

### 检索的两级流水线：收紧已做，宽进仍缺

本 step 的检索已是一半的两级流水线——**「收紧」那一半做完了**（rerank 精排，见 §2），剩下的缺口在**「宽进」**：召回只有向量这一路（**稠密检索**），衡量的是语义相近——字面精确匹配反而可能失手：查询里带着确切科目名、产品编号、人名这类「语义撑不住、只能靠字面」的词时，含这个词的 chunk 未必是向量最近邻。生产级的标配是**混合检索（hybrid，稀疏 + 稠密）**：向量一路之外再配一路稀疏检索（如 BM25，按查询词出现与否、出现多少打分），两路各出 Top-K 再合并——跨路分数不可比，按 chunk ID 归并去重，用 RRF（倒数排名融合）按排名而非原始分排序。稠密保语义，稀疏保字面。

画成图（R/A/G 各管哪段也标了出来），生产级的检索就是这样一条两级流水线，本项目走到哪一步也标了出来：

```
┌ R（检索）──┐
│        查询
│         │
│   ┌─────┴─────┐
│   │           │
│ BM25        向量        ← 稀疏（字面）+ 稠密（语义），两路召回
│  ✗未做      ✓本仓
│   └─────┬─────┘
│         ↓
│     Top 50~100           ← 粗排：宽进，保召回（本仓：单路 Top-20）
│         ↓
│     rerank 精排          ← ✓本仓已加（智谱 rerank API）
│   ┌─────┴─────┐
│   │           │
│Cross-Encoder  LLM Reranker
│快、便宜、稳定  慢、贵、能理解复杂规则
│   └─────┬─────┘
│         ↓
│      Top 5~10            ← 出口收紧，保精度（本仓：Top-3）
└─────────┼──┘
          ↓
   A（增强）：拼 context + system 约束
          ↓
   G（生成）：Generation LLM
```

稠密一路还有个盲区：它永远给得出分数——问「分红」，照样给 0.58 的「话题像」分，证不了「没有」；稀疏一路按字面计分，查询词没出现就是零分，「字面不存在」在检索阶段就看得见，不必全靠 LLM 兜底。

整条链路的分工可以用一句话记：**Retriever 负责「别漏掉」，Reranker 负责「排得准」，LLM 负责「读懂并回答」**。漏斗越往后越贵，喂的也就越少——全库筛成几十条，精排成几条，最贵的 LLM 只读最好的那几条。

拼 context 本身还剩两个工程问题：**token 预算**——上下文窗口有限，Top-K 取多大、加起来超了怎么截断；**引用粒度**——本 step 是 chunk 级，`根据[2]` 能定位回那个约 400 字的块，但「4,663,116,528.38 出自块里哪一行」要用户自己找。生产级要**句子级**：答案里每个论断精确指回支撑它的那句原文——难在答案句往往是 LLM 改写、合并出来的，原文里没有现成的对应句。

这些剩下的——**混合检索、RRF 融合、句子级引用**——都是生产级 RAG 在这个骨架上继续加的东西，但无论怎么叠，「检索回来拼进 prompt、让 LLM 看着资料答」这个内核不变。本项目止步于「朴素 RAG + rerank 精排」：两级检索的收紧半程 + 拼 context + system 约束 + 生成，把闭环走通、看清每一步在做什么。
