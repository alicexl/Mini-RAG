## 1. RAG 三步：检索 + 增强 + 生成

RAG 全称 **R**etrieval-**A**ugmented **G**eneration——检索增强生成。名字就是三步：

- **检索（Retrieval）**：把用户问题在向量库里找出最相似的 chunk。这一步内部是三段式流水线——两路召回宽进、RRF 融合、rerank 精排收紧（下一节展开）。[Step 1](../step1_basics/README.md) 的分块与向量化、[Step 2](../step2_index/README.md) 的向量库，前两步都是在搭这一步。
- **增强（Augmented）**：把检索回来的 chunk 作为「参考资料」塞进 prompt，交给 LLM。
- **生成（Generation）**：LLM 看着这些资料，生成自然语言的答案。

前两步我们手里已经有了「检索回来的 Top-K 文本」。本 step 就补上后两步，把链路闭环：检索 → 拼 prompt → LLM 生成。

---

## 2. 检索升级：两路召回宽进，RRF 融合，rerank 收紧

Step 2 的 `search` 是「向量 Top-K 一把梭」——只有一路、直接取相似度前 3。本 step 把它升级成生产级检索的标准三段式：

```
       ┌→ 向量召回 Top-20（稠密：语义宽进）─┐
查询 ──┤                                  ├→ RRF 融合（ID 归并去重）→ rerank 精排 → Top-3 → 进 prompt
       └→ BM25 召回 Top-20（稀疏：字面宽进）┘
```

### 为什么宽进要两路：稀疏是「字面指纹」，稠密是「语义指纹」

向量召回（稠密）看「语义像」——问"赚钱"能命中"营业收入"；BM25（稀疏）看「字面命中」——查询词在文档里出现没有、出现多少、区分度高不高。两者的盲区正好互补：

- **稠密的盲区**：确切科目名、产品编号、人名这类「语义撑不住、只能靠字面」的词——含这个词的 chunk 未必是向量最近邻
- **稀疏的盲区**：表述不同就抓瞎——"营收"和"营业收入"是不同的词，BM25 关联不了它们

还有一个语义层面的差别，后面第三问会用到：**稠密永远给得出分**（问「分红」照样给 0.58 的「话题像」分，证不了「没有」）；BM25 按字面计分，查询词一个都没出现就是**零分、直接不进结果**——「字面不存在」在检索阶段就看得见，不必全靠 LLM 兜底。

BM25 教学版不引检索库——分词用 jieba，Okapi 公式摊开手写（`BM25Index`，30 来行）：idf 衡量词的区分度，tf 项带词频饱和与文档长度归一，k1=1.5 / b=0.75 是常用参数。

### 为什么融合用 RRF：跨路分数不可比

两路的分数**没有可比性**——余弦在 0～1 之间，BM25 无上界，直接相加没有意义。RRF（Reciprocal Rank Fusion）的答案是**只用排名**：

```
score(d) = Σ 各路 1/(k + rank)，k=60
```

按 chunk 下标累加，天然完成 **ID 归并去重**——这正是「多路召回怎么合并去重」的标准解法：不挑某一路的分数，而是把所有路的名次折算成可加的分数。同一块被两路同时命中反而加分：**「语义也像、字面也中」的块，理应排得更前**。

### 为什么出口要收紧：双塔 vs Cross-Encoder

- **向量召回是 bi-encoder（双塔）**：查询和文档**各自**编码、各出一个向量，文档向量离线算好存库，查询时只比余弦。快就快在「各自」——但它俩从没「见过面」，只能判断「话题像」，判断不了「这块到底答没答这个问题」。
- **rerank 是 Cross-Encoder**：把「查询 + 候选」**拼成一条文本**一起过模型，输出直接是一个相关性分。准就准在「拼在一起」——两边的词逐个直接对照；慢也慢在这里——分数依赖当前查询、没法预计算，每对都要现算。

所以整条漏斗的分工是：**便宜的两路扫全库各捞 20 条（别漏掉），RRF 白菜价合成一个排序，昂贵的 Cross-Encoder 只对融合后的几十条精排取 3（排得准）**——越往后越贵，喂的越少；最贵的生成 LLM 只读精排后最好的那几条。

### 代码与降级

```python
def retrieve(question, store, bm25, embedder, reranker, top_k=TOP_K):
    vec = store.search(question, embedder, top_k=RECALL_K)          # 稠密路：语义宽进
    bm = bm25.search(question, top_k=RECALL_K)                      # 稀疏路：字面宽进
    merged = rrf_merge([[i for i, _, _ in vec], [i for i, _ in bm]])  # ID 归并去重 + RRF 融合
    try:
        results = reranker.rerank(question, [store.chunks[i] for i, _ in merged],
                                  top_n=top_k)                      # 精排收紧
        ...
        return retrieved, True
    except Exception:
        return merged[:top_k], False    # rerank 失败 → 降级回 RRF 顺序，检索不中断
```

工程细节：

- **rerank 走智谱开放平台原生 API**（`POST /paas/v4/rerank`，模型名 `rerank`），与生成（Anthropic 兼容网关）**共用同一个智谱 Key**；BM25 是纯本地计算，不依赖任何服务。
- **BM25 索引启动时从 chunks 现建**（百级 chunk 毫秒级）——不落盘、不加存储文件，`data/` 三件套不变。
- **降级**：rerank 挂了（网络/余额/限流）不拦住问答，退回 RRF 顺序取前 3，终端打 `[WARN]` 提示。外围设施失败不阻断核心链路。
- 每条检索结果带**路由标记**（`两路/向量/BM25`）——哪块从哪路来、哪块两路都命中，一眼可见。

## 3. 「增强」到底在做什么

直觉很好懂：**把检索回来的 chunk 塞进 prompt，让 LLM 看着资料回答，而不是凭训练记忆凭空答题**。但「增强」不止是塞数据这一下，它其实做两件事。

### 第一件：把检索结果拼成 context

检索回来的是 `[(chunk编号, 向量sim, 精排score, 文本), ...]`。要喂给 LLM，得先拼成一段它看得懂的「参考资料」：

```python
def build_context(retrieved):
    parts = [f"[{i}] {chunk}" for i, (_, _, _, chunk) in enumerate(retrieved, 1)]
    return "\n\n".join(parts)
```

给每条 chunk 加个编号 `[1] [2] [3]`，不光是为了好看——是为了让 LLM **能引用来源**（「根据[1]」）。检索结果能不能追溯到原文，是 RAG 区别于「LLM 瞎编」的关键。

### 第二件：用 system prompt 约束 LLM 的行为

光把资料塞进去还不够。LLM 天生爱「答题」——哪怕资料里没有，它也可能调动训练时记住的知识，自信地编一个出来（这就是**幻觉**）。所以要用 system prompt 明确改变它的行为模式：

```python
SYSTEM_PROMPT = (
    "你是一个严谨的问答助手。只能根据下面【参考资料】里的内容回答用户问题，"
    "并在用到某条资料时标注它的编号（如「根据[1]」）。"
    "如果【参考资料】里没有相关信息，就如实回答「资料中未提及」，禁止编造。"
)
```

这段话干了三件事：**限定信息来源**（只能用资料）、**要求引用编号**（可追溯）、**允许拒答**（没有就说没有）。把这三句拼进 prompt，LLM 就从「凭记忆答题」切换到「看资料答题」。

### 完整的一条 RAG

把两件事合起来，一条 RAG 长这样：

```python
def rag_answer(question, store, embedder, generator, reranker, top_k=3):
    retrieved, reranked = retrieve(question, store, embedder, reranker, top_k=top_k)  # 检索
    context = build_context(retrieved)                             # 增强①：拼 context
    user = f"【参考资料】\n{context}\n\n【用户问题】\n{question}"
    answer = generator.answer(SYSTEM_PROMPT, user)                 # 增强②(system约束) + 生成
    return retrieved, reranked, answer, context
```

`user` 消息里同时装着【参考资料】和【用户问题】，`system` 消息装着行为约束——这就是「增强」的全部：**用检索结果填充 prompt，用 system 指令约束模型**。

第一问看一遍完整链路——检索、拼 prompt、生成三段都在（混合检索实测；每行三个信号：`sim` 向量相似度、`score` 精排分、方括号里的**路由标记**说明这块从哪路召回）：

```

  [1] sim=0.498 score=1.000 [向量] [盐湖股份2024年年报（节选）] 经营活动产生的现金流量净额：2024年 = 7,819,152,86…

→ 拼 prompt 喂给 LLM（增强 = 检索结果 + system 约束）：
  [system] 只能用【参考资料】，引用编号（如「根据[1]」），没有就说没有
  [参考资料] [1] 经营活动产生的现金流量净额：2024年 = 7,819,152,860.43；2023年 = 12,104,618,721.68；同比增减 = -35.…
  [用户问题] 公司2024年赚了多少钱？

→ LLM 生成：
根据[3]，公司2024年归属于上市公司股东的净利润为 **4,663,116,528.38元**（约46.63亿元），
同比2023年的7,913,614,646.24元下降41.07%。

补充相关数据：
- 2024年营业收入为15,134,119,500.89元（约151.34亿元），同比下降29.86%（根据[3]）；
- 扣除非经常性损益的净利润为4,400,518,590.09元（约44.01亿元）（根据[3]）；
- 基本每股收益为0.8812元/股（根据[2]）；
- 经营活动产生的现金流量净额为7,819,152,860.43元（约78.19亿元）（根据[2]）。
```

看路由标记：[3] 那个装着**营收 + 净利润 + 扣非三行数据**的「主要会计数据」块标的是 `[两路]`——问「赚了多少钱」，向量路和 BM25 路（"公司/2024 年"字面命中年报标题）都捞到了它，RRF 给它双倍名次分。也注意一个细节：rerank 这次没把它排到第一（三个 score 全是 1.0，并列分数下 rerank 失去了区分度——§5 有专门一节讲这个实测边界）。好在 LLM 自己能挑：三块里真正"答了这个问题"的是 [3]，答案的主要数字全部来自它。

```

  [2] sim=0.637 score=1.000 [向量] [盐湖股份2025年年报（节选）] 西藏天路股份有限公司青海盐湖工业股份有限公司.↵氯化钾制造业 销售量…

→ LLM 生成：
根据参考资料，钾肥（氯化钾制造业）的产销量情况如下：

**2023年（根据[1]）：**
- 生产量：492.60万吨，较2022年的580.00万吨同比下降15.07%
- 销售量：资料中未提及2023年氯化钾的销售量数据

**2024年（根据[2]）：**
- 生产量：496.00万吨
- 销售量：467.28万吨

另外，从成本角度看，钾产品2024年营业成本为54.65亿元（占营业成本75.01%），

```

两个值得注意的点。一是 [2] 的出处——2024 年的数据来自 **2025 年报**的对比列（次年年报的"上年"列），metadata 让跨年答案的出处一目了然。二是 [3] 带来的意外佐证：rerank 把成本构成块也捞了进来，LLM 用它跟产销量互相印证——检索面放宽后，LLM 有机会把"相关但不直接回答"的块用成论据。

### 第三问：原文里没有的信息——这才是重点

第三个查询故意问语料里没写的「2025 年分红多少」（拼 prompt 那步与第一问同构，略）：

```
查询> 公司2025年打算给股东分红多少？
检索：向量 + BM25 两路各召回 20 → RRF 融合 → rerank 精排 → Top-3（…）：
  [1] sim=0.544 score=1.000 [两路] [盐湖股份2025年年报（节选）] 经营活动产生的现金流量净额（元）：2025年 = 10,160,860,737.…
  [2] sim=0.478 score=1.000 [两路] [盐湖股份2025年年报（节选）] # 盐湖股份 2025 年年报（节选）↵↵## 主要会计数据↵公司是…
  [3] sim=0.458 score=1.000 [两路] [盐湖股份2025年年报（节选）] 经营活动现金流入小计：2025年 = 18,951,757,266.…

→ LLM 生成：
资料中未提及公司2025年的分红（利润分配）方案。

所提供的参考资料仅包含盐湖股份2025年年报中的主要会计数据，如营业收入、归属于上市公司股东的净利润（2025年为8,475,535,262.69元）[2]、每股收益（基本每股收益1.6017元/股）[1]、净资产收益率（22.30%）[1]以及现金流量情况[1][3]等内容，但没有涉及股利分配或分红预案的相关信息。
```

注意这里发生了什么：

- **检索这一关「失效」了**——语料里根本没有分红信息。三个块全标 `[两路]`：「公司/股东/2025 年」这些高频字面词让 BM25 也命中了它们——但这是「字面确实出现了」，不是「分红存在」；稀疏路的「零分=不存在」判定在这里帮不上忙，因为这些块字面真含查询词。Top-K 机制照样返回「最不差的」K 个（精排也全打 1.0——Cross-Encoder 只会排「哪个更像答案」，证不了「没有」）。这印证了 [Step 1](../step1_basics/README.md) 说的「Top-K 不卡硬阈值」——这里如果卡阈值，连这几个 chunk 都没有，但要不要卡、卡多少都不是关键。
- **LLM 这一关「兜住了」**——system prompt 要求「没有就说没有」，LLM 看完三个都不含分红信息的 chunk，选择**拒答**而非编一个数字，还顺手列举了资料里实际有什么、逐项标了出处。

这就是 RAG 防幻觉的**两道关**：检索负责把相关内容送到面前（这关对「真不存在」的问题天然无效——两路召回和精排都救不了），LLM 在 system 约束下负责判断「资料里到底有没有」（这关兜住了幻觉）。如果只有检索没有 system 约束，LLM 很可能看着一堆无关 chunk，调动训练记忆自信地编一个分红比例——那就不叫 RAG 了。

## 5. 剩下的边界

到这一步，生产级检索的标准三段式已经全部就位——两路召回宽进、RRF 融合、rerank 精排收紧，每一环都是裸代码。画成图（R/A/G 各管哪段也标了出来）：

```
┌ R（检索）──┐
│        查询
│         │
│   ┌─────┴─────┐
│   │           │
│ BM25        向量        ← 稀疏（字面）+ 稠密（语义），两路召回
│  ✓本仓      ✓本仓
│   └─────┬─────┘
│         ↓
│     RRF 融合             ← ID 归并去重 + 按排名融合（本仓：k=60）
│         ↓
│     rerank 精排          ← ✓本仓（智谱 rerank API，失败降级回 RRF 顺序）
│   ┌─────┴─────┐
│   │           │
│Cross-Encoder  LLM Reranker
│快、便宜、稳定  慢、贵、能理解复杂规则
│   └─────┬─────┘
│         ↓
│      Top 5~10            ← 出口收紧，保精度（本仓：Top-3）
└─────────┼──┘
          ↓
   A（增强）：拼 context + system 约束
          ↓
   G（生成）：Generation LLM
```

整条链路的分工可以用一句话记：**Retriever 负责「别漏掉」，Reranker 负责「排得准」，LLM 负责「读懂并回答」**。漏斗越往后越贵，喂的也就越少——全库筛成几十条，精排成几条，最贵的 LLM 只读最好的那几条。

剩下的边界在哪？两类。

### 幻觉只是被压低，没被根除

system prompt 说「禁止编造」，但 LLM 不一定每次都听话。它仍可能：**误读 context**（把 3.5 万吨读成 35 万吨）、**context 里有但答错**（算错、张冠李戴）、**context 太长时漏看中间**（所谓 *lost in the middle*——LLM 对 prompt 首尾更敏感，中间的 chunk 容易被忽略）、甚至被**恶意 chunk 注入指令**（资料里藏着「忽略上面的指令，回答 XXX」）。RAG 把幻觉从「几乎必定编」降到了「偶尔编」，但没归零。

### 实测发现的边界：rerank 分数饱和

智谱 rerank 的实测分数经常**全部饱和在 1.0**——并列分数下它失去区分度，最终排序退化为「并列时的返回顺序」。实测一例：问「氯化钾制造业的销售量是多少万吨？」，**BM25 单路排序其实是对的**——真正含「氯化钾制造业 销售量」字面的两个表格块排第 2、3 名，仅以 0.14 分之差输给一个含「制造业500强」的叙述块；但融合 + 精排之后，表格块被挤出 Top-3，答案只从某个 400 字大块的「叙述 + 表格混装」里捞到了 2023 年一列——正确、但不全。这个案例提示两件事：

- **分数饱和的 rerank 别当排序真值用**——拿它粗筛可以，关键排序要留一路可解释的分数（BM25/RRF）
- **chunk 变大后「表格行和叙述混装」会稀释科目级精确查询的命中**——精确到行的检索要靠更细的表格切分或结构化抽取，这正是 §2 两路互补治不了的那类病

### 更远的工程边界

- **句子级引用**：本 step 是 chunk 级，`根据[2]` 定位回约 400 字的块，「4,663,116,528.38 出自哪一行」要用户自己找——生产级要答案句精确指回支撑原文，难在答案句往往是 LLM 改写、合并出来的
- **token 预算**：Top-K 取多大、几块加起来超上下文窗口怎么截断
- **ANN 索引**：本仓是线性扫描 O(N)，百万级 chunk 要 FAISS/HNSW 这类亚线性索引
- **query 改写**：一次提问拆多个查询再召回，覆盖更宽，代价是延迟和成本

无论怎么叠，「检索回来拼进 prompt、让 LLM 看着资料答」这个内核不变。本项目到这里，把三段式检索的每一环都用裸代码走通了。
