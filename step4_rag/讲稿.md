# Step 4 讲稿：完整 RAG —— 检索增强生成

---

## 一、RAG 三步：检索 + 增强 + 生成

RAG 全称 **R**etrieval-**A**ugmented **G**eneration——检索增强生成。名字就是三步：

- **检索（Retrieval）**：把用户问题变成向量，在向量库里找出最相似的 Top-K 个 chunk。[Step 1](../step1_embedding/讲稿.md) 的 embedding、[Step 2](../step2_chunking/讲稿.md) 的切块、[Step 3](../step3_index/讲稿.md) 的向量库，前整整三章都是在搭这一步。
- **增强（Augmented）**：把检索回来的 chunk 作为「参考资料」塞进 prompt，交给 LLM。**这一步是本章的重点**——前三章都为它铺路。
- **生成（Generation）**：LLM 看着这些资料，生成自然语言的答案。

前三章我们手里已经有了「检索回来的 Top-K 文本」。Step 4 就补上后两步，把链路闭环：检索 → 拼 prompt → LLM 生成。

---

## 二、「增强」到底在做什么

直觉很好懂：**把检索回来的 chunk 塞进 prompt，让 LLM 看着资料回答，而不是凭训练记忆凭空答题**。但「增强」不止是塞数据这一下，它其实做两件事。

### 第一件：把检索结果拼成 context

检索回来的是 `[(chunk编号, 相似度, 文本), ...]`。要喂给 LLM，得先拼成一段它看得懂的「参考资料」：

```python
def build_context(retrieved):
    parts = [f"[{i}] {chunk}" for i, (_, _, chunk) in enumerate(retrieved, 1)]
    return "\n\n".join(parts)
```

给每条 chunk 加个编号 `[1] [2] [3]`，不光是为了好看——是为了让 LLM **能引用来源**（「根据[1]」）。检索结果能不能追溯到原文，是 RAG 区别于「LLM 瞎编」的关键。

### 第二件：用 system prompt 约束 LLM 的行为

光把资料塞进去还不够。LLM 天生爱「答题」——哪怕资料里没有，它也可能调动训练时记住的知识，自信地编一个出来（这就是**幻觉**）。所以要用 system prompt 明确改变它的行为模式：

```python
SYSTEM_PROMPT = (
    "你是一个严谨的财报问答助手。只能根据下面【参考资料】里的内容回答用户问题，"
    "并在用到某条资料时标注它的编号（如「根据[1]」）。"
    "如果【参考资料】里没有相关信息，就如实回答「资料中未提及」，禁止编造。"
)
```

这段话干了三件事：**限定信息来源**（只能用资料）、**要求引用编号**（可追溯）、**允许拒答**（没有就说没有）。把这三句拼进 prompt，LLM 就从「凭记忆答题」切换到「看资料答题」。

### 完整的一条 RAG

把两件事合起来，一条 RAG 长这样：

```python
def rag_answer(question, store, embedder, generator, top_k=3):
    retrieved = store.search(question, embedder, top_k=top_k)      # 检索
    context = build_context(retrieved)                             # 增强①：拼 context
    user = f"【参考资料】\n{context}\n\n【用户问题】\n{question}"
    answer = generator.answer(SYSTEM_PROMPT, user)                 # 增强②(system约束) + 生成
    return retrieved, answer, context
```

`user` 消息里同时装着【参考资料】和【用户问题】，`system` 消息装着行为约束——这就是「增强」的全部：**用检索结果填充 prompt，用 system 指令约束模型**。

## 三、动手：完整链路

demo 是**两个命令**（按用户场景划分，不是按实现步骤）：`ingest` 导入文档，`chat` 交互问答。语料是真实的盐湖股份年报节选（`sample_reports/` 下三份，由 `build_excerpts.py` 从年报 PDF 生成）。

**第一步，导入文档：**

```
PYTHONUTF8=1 python step4_rag/demo.py ingest sample_reports/盐湖股份2023年年报（节选）.md
[OK]「盐湖股份2023年年报（节选）」：13999 字 → 84 块，向量矩阵 (84, 1024)
```

`ingest` 跑的就是前三章那条链：读文档 → 切块(step2) → 向量化(step1) → 入库(step3)，来源名取文件名（写进 metadata 的 source），存在 `data/` 三件套里。**幂等**：同一份文档再导一次会提示 `[SKIP] 已在库中`。把 2024、2025 两份也导进来，库里就有横跨三个年度的 234 个 chunk。

**第二步，启动交互式问答 terminal：**

```
PYTHONUTF8=1 python step4_rag/demo.py chat
向量库：234 个 chunk（检索 qwen3-embedding:0.6b / 生成 glm-5.2）
```

（生成模型走智谱 GLM 网关，API Key 三选一：环境变量 `ANTHROPIC_API_KEY`、改 demo.py 顶部 `API_KEY` 常量、或运行时按提示输入；检索部分用本地 Ollama，无需配置。）

### 前两问：答案在检索回来的 chunk 里

第一问看一遍完整链路——检索、拼 prompt、生成三段都在：

```
查询> 公司2024年赚了多少钱？
检索 Top-3（[1][2][3] 即 LLM 回答里「根据[1]」的引用；方括号里是元信息来源）：
  [1] sim=0.588 [盐湖股份2024年年报（节选）] 经营活动产生的现金流量净额（元）：2024年 = 7,819,152,860.43；2023…
  [2] sim=0.575 [盐湖股份2024年年报（节选）] 归属于上市公司股东的净利润（元）：2024年 = 4,663,116,528.38；2023…
  [3] sim=0.572 [盐湖股份2024年年报（节选）] 总资产（元）：2024年末 = 45,782,850,934.85；2023年末 = 46,…

→ 拼 prompt 喂给 LLM（增强 = 检索结果 + system 约束）：
  [system] 只能用【参考资料】，引用编号（如「根据[1]」），没有就说没有
  [参考资料] [1] 经营活动产生的现金流量净额（元）：2024年 = 7,819,152,860.43；2023…
  [用户问题] 公司2024年赚了多少钱？

→ LLM 生成：
公司2024年归属于上市公司股东的净利润 4,663,116,528.38元、扣除非经常性损益的净利润 4,400,518,590.09元（均根据[2]），基本每股收益 0.8812元/股（根据[1]）。
```

两点值得注意。一是检索结果方括号里的来源就是 metadata，答案出自哪份年报一目了然。二是 LLM 没被排第一的 [1]（现金流）带偏，从 [2]（净利润行）抽出真正的"赚了多少钱"——它能区分"哪个 chunk 才是问题的答案"。

三个年度的语料在同一库里，跨年问题也答得动。问「2023年和2024年，钾肥产销量分别是什么水平？」，Top-1 直接命中产销量表的行——"氯化钾制造业 销售量 万吨：2024年 = 467.28；2023年 = 560.00；同比增减 = -16.56%"，销量、产量、同比在同一个 chunk 里相邻都齐，LLM 把两年的销量产量全抽了出来，每条都标了来源：

> 销量：2024年 467.28 万吨、2023年 560.00 万吨（同比 -16.56%，根据[1]）；生产量：2024年 496.00 万吨、2023年 492.60 万吨（同比 +0.69%，根据[1]）。

这就是「看着资料回答」的样子：答案来自检索到的 chunk，而不是 LLM 的记忆。

### 第三问：原文里没有的信息——这才是重点

第三个查询故意问语料里没写的「2025 年分红多少」（拼 prompt 那步与第一问同构，略）：

```
查询> 公司2025年打算给股东分红多少？
检索 Top-3：
  [1] sim=0.588 [盐湖股份2025年年报（节选）] 归属于上市公司股东的净利润（元）：2025年 = 8,475,535,262.69；2024…
  [2] sim=0.584 [盐湖股份2025年年报（节选）] 稀释每股收益（元/股）：2025年 = 1.6017；2024年 = 0.8812（同比 8…
  [3] sim=0.566 [盐湖股份2025年年报（节选）] 经营活动产生的现金流量净额（元）：2025年 = 10,160,860,737.41；202…

→ LLM 生成：资料中未提及。
```

注意这里发生了什么：

- **检索这一关「失效」了**——语料里根本没有分红信息，检索器自然找不到相关 chunk。但 Top-K 机制总会返回「最不差的」K 个，于是把 2025 年报的净利润、每股收益、现金流这些相关但答非所问的 chunk 照样塞进了 context（最高相似度才 0.588）。这印证了 [Step 1](../step1_embedding/讲稿.md) 说的「Top-K 不卡硬阈值」——这里如果卡阈值，连这几个 chunk 都没有，但要不要卡、卡多少都不是关键。
- **LLM 这一关「兜住了」**——system prompt 要求「没有就说没有」，LLM 看完三个都不含分红信息的 chunk，选择**拒答**而非编一个数字。

这就是 RAG 防幻觉的**两道关**：检索负责把相关内容送到面前（这关对「真不存在」的问题天然无效），LLM 在 system 约束下负责判断「资料里到底有没有」（这关兜住了幻觉）。如果只有检索没有 system 约束，LLM 很可能看着一堆无关 chunk，调动训练记忆自信地编一个分红比例——那就不叫 RAG 了。

## 四、朴素 RAG 的边界

这一章拼出了完整的 RAG 闭环，但它仍是教学版，有几个层面的局限，生产级 RAG 都要继续解决。

### 幻觉只是被压低，没被根除

system prompt 说「禁止编造」，但 LLM 不一定每次都听话。它仍可能：**误读 context**（把 3.5 万吨读成 35 万吨）、**context 里有但答错**（算错、张冠李戴）、**context 太长时漏看中间**（所谓 *lost in the middle*——LLM 对 prompt 首尾更敏感，中间的 chunk 容易被忽略）、甚至被**恶意 chunk 注入指令**（资料里藏着「忽略上面的指令，回答 XXX」）。RAG 把幻觉从「几乎必定编」降到了「偶尔编」，但没归零。

### context 拼装本身是一堆工程问题

- **token 预算**：上下文窗口有限（几千到几十万 token），Top-K 取多大、加起来超了怎么截断？
- **相关性里混着噪音**：Top-K 里排在后面的往往相关性已经很弱。第三问最典型——Top-3 照样召回一堆「话题像」但答非所问的块，硬喂给 LLM 反而干扰。生产级 RAG 因此在检索后加一道 **rerank（精排）**：用一个更强的模型把「问题 + 候选 chunk」拼在一起逐条打分，只把真正能回答问题的几条挑出来再拼。它准在两边逐词对照（embedding 是各自编码再比对，只知道话题像），慢在每对都要现算、不能像向量那样预计算——所以只对检索回来的几十条跑。
- **来源引用**：本章是 **chunk 级**——`根据[2]` 能定位回那个约 200 字的块，但「4,663,116,528.38 出自块里哪一行」要用户自己找。生产级要**句子级**：答案里每个论断精确指回支撑它的那句原文（悬停答案某句、原文恰好那句高亮）——而答案句往往是 LLM 改写、合并出来的，原文里没有现成的对应句。

### 检索的缺口：只认「语义像」，会漏「字面命中」

本章的检索只有向量这一路（**稠密检索**），衡量的是语义相近——字面精确匹配反而可能失手：查询里带着确切科目名、产品编号、人名这类「语义撑不住、只能靠字面」的词时，含这个词的 chunk 未必是向量最近邻。生产级的标配是**混合检索（hybrid，稀疏 + 稠密）**：向量一路之外再配一路稀疏检索（如 BM25，按查询词出现与否、出现多少打分），两路各出 Top-K 再合并——稠密保语义，稀疏保字面。

它和上面的 rerank 正好一对：混合检索解决「该捞的没捞回来」（保召回），rerank 解决「捞回来的混着噪音」（保精度）——入口放宽，出口收紧。稠密一路还有个盲区：它永远给得出分数——问「分红」，照样给 0.58 的「话题像」分，证不了「没有」；稀疏一路按字面计分，查询词没出现就是零分，「字面不存在」在检索阶段就看得见，不必全靠 LLM 兜底。

这些——**混合检索、rerank 精排、句子级引用**——都是生产级 RAG 在这个骨架上继续加的东西，但无论怎么叠，「检索回来拼进 prompt、让 LLM 看着资料答」这个内核不变。本项目止步于「朴素 RAG」：检索 + 拼 context + system 约束 + 生成，把闭环走通、看清每一步在做什么。
