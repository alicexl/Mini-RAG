# Step 1 讲稿：文本向量化 —— 理解 Embedding

---

## 一、从一个问题开始

假设你在文档库里搜"盐湖股份2024年赚了多少钱"，但文档里写的是"盐湖股份2024年营业收入150亿元"。如果检索只按字面匹配——拿"赚""多少钱"这些字去比对——它根本找不到，因为"赚"字压根没出现。

人类一眼就知道"赚钱"和"营业收入"是一回事，但只认字面的机器看到的是两串毫不相干的字符——"赚"和"营收"连个共同字都没有，怎么判断它们相关？

**Embedding 就是解决这个问题的桥梁——它把文本变成向量，让语义相近的文本，对应的向量也更相似。**

---

## 二、Embedding 怎么工作

### 语义坐标：给文本一个"位置"

假设我们只用两个维度来理解文本——"金融感"和"自然感"：

```
盐湖股份2024年营收150亿：  [0.9, 0.1]    很金融，不自然
盐湖股份2023年营收134亿：  [0.85, 0.1]   也很金融，不自然
今天天气不错：              [0.1, 0.9]    不金融，很自然
```

画在坐标纸上，两个营收句子挨在一起，天气句子离它们很远。**距离反映了语义关系——不需要人工标注，向量空间自然形成了语义聚类。**

真实的 Embedding 模型做的是同样的事，只不过不是 2 个维度，而是 **1024 个**（以 qwen3-embedding:0.6b 模型为例）。每个维度不再是人类能命名的"金融感""自然感"，而是模型自己学出来的抽象特征——但效果一样：语义相近的文本，坐标接近。

**你不需要关心这 1024 个数字分别代表什么**——就像你不需要知道 GPS 坐标的每个数字代表什么，你只需要知道：坐标越近，地点越近。向量也是一样：向量越近，语义越近。

### 怎么变向量：模型内部的四步

文本发过去，拿回一串浮点数。**那模型内部做了什么？** embedding 模型把文本变成向量，可以拆成四步：

```
"盐湖股份2024年营收150亿"
        │
        ▼
① 分词：切成 token
[盐湖, 股份, 2024, 年, 营收, 150, 亿]      ← 仅示意，实际由模型自带的 tokenizer 切分
        │
        ▼
② 查表：每个 token 查 Embedding 表，取出初始向量
[向量₁, 向量₂, 向量₃, ...]     ← 每个 1024 维，此时还是一串
        │
        ▼
③ 上下文化：多层 Transformer 让每个 token "看到" 其他 token
[向量₁', 向量₂', 向量₃', ...]   ← 仍是一串，但每个都融入了上下文
        │
        ▼
④ 池化（pooling）：把一串向量合成一个（通常取平均）
[0.023, -0.157, 0.891, ...]    ← 最终代表整句话的 1024 维向量
```

第 ① 步是**分词**——模型把文本切成一个个小单元（token）。切法用的是**模型自带的 tokenizer**——它在预训练时就定死了（所以同一个句子换一个 embedding 模型，切出来的 token 可能就不一样），中文里常见词往往占一个 token，生僻的会拆成更小的子词。

第 ② 步是**查 Embedding 表**——每个 token 在表里有一行预训练好的向量。注意此时还是**一串**向量（有几个 token 就有几个），而且查出来的是**静态向量**：同一个 token 永远对应同一行——**两个"苹果"查表会得到完全一样的向量**，因为它此刻还不知道自己出现在哪句话里。

第 ③ 步是 **Transformer 的核心**，专门修掉"静态向量"这个缺陷：**同一个词在不同句子里意思完全不同**。比如"苹果"——

```
"苹果 很好吃"       → 苹果是水果
"苹果 发布 新手机"  → 苹果是公司
```

第 ③ 步让每个 token 去**看句子里其他所有 token**（这就是 Attention 机制），根据上下文修正自己的向量：

```
"苹果 很好吃"       → 苹果看到了"好吃"       → 苹果向量变成 [4, 8, 2]
"苹果 发布 新手机"  → 苹果看到了"发布""手机"  → 苹果向量变成 [9, 1, 6]
```

（向量是示意，真实是 1024 维浮点。）同样是"苹果"，经过 Transformer 后变成了**完全不同**的向量——上下文把它的含义"定型"了。

一句话区分两个术语：第 ② 步查表得到的是**静态向量**（Static Embedding）——给每个词一个固定含义（查字典）；第 ③ 步 Transformer 输出的是**上下文化向量**（Contextual Embedding）——让每个词根据上下文修正自己的含义。

第 ④ 步才是真正的"变一个"——**池化**（pooling），最常见就是把这串向量**取平均**，得到一个代表整句话的 1024 维向量。注意第 ③ 步的 Attention 只负责让 token 互相"看"、修正各自向量（出来仍是一串），真正把"一串"压成"一个"的是这一步的取平均，不是 Attention。

**关键认知：向量是模型算出来的，不是我们定义的。**

我们只负责把文本喂进去、把向量取出来。语义结构是训练过程"压"进模型参数里的——这套语义从哪来？模型先在网页、书籍、维基等海量通用文本上预训练（和 LLM 同一锅语料），再用上千万对"查询-文档"（搜索日志、问答数据，加上 LLM 合成的问答对）做对比微调，成对地告诉模型"哪些文本语义相关"，让它学会在向量空间里把相关的拉近、无关的推开。这也是为什么你只喂 5 段文本，它却带着整套预训练的语义知识。

这套"从上下文共现里学语义"的思路，可以追溯到 1957 年语言学家 Firth 的那句格言：

> *"You shall know a word by the company it keeps."*
>
> "一个词的意思，由它的邻居决定。"

Embedding 空间里的每一个位置，都是统计共现关系的结晶。

### 怎么算"远近"——余弦相似度

有了向量，怎么衡量两个文本的语义相似度？这里先澄清一个常见误区。

Embedding 模型的目标其实只有一句话：**语义越相近，在向量空间里越接近**。它只负责把文本"摆"进空间——让"苹果"离"香蕉"近、离"Python"远，这件事就算完成了。至于这个"近"具体怎么算、用哪种公式，是**检索算法**决定的，不是 Embedding 模型规定的。很多教程一上来就讲余弦相似度，容易让人误以为"Embedding 就是为余弦设计的"——其实不是，"近"可以有好几种度量：

- **欧氏距离**（Euclidean）：高中学的两点直线距离 √((x₁−x₂)²+...)，越小越相似
- **余弦相似度**（Cosine）：不看长度，只看两个向量**方向**是否一致，最常用
- **点积**（Dot Product）：a·b 越大越相似，有些模型和向量数据库直接用它
- **曼哈顿距离**（Manhattan）：|x₁−x₂|+|y₁−y₂|，NLP 里很少用，但理论上也行

**为什么 RAG 几乎都用余弦？** 因为 embedding 向量的**长度常常没有意义**。比如"苹果"被映射成 [1, 2]，换一种情况可能映射成 [100, 200]——两者表达的语义完全一样，只是整体放大了 100 倍。用欧氏距离算，它们离得很远，会被误判成"不像"，这显然不合理；余弦相似度只看方向，[1, 2] 和 [100, 200] 方向完全一致，算出来就是 1，正确判定为"语义一样"。

余弦相似度的公式：

```
cos(θ) = (A · B) / (‖A‖ × ‖B‖)

值域: [-1, 1]
 1  = 方向完全一致（极其相似）
 0  = 正交（不相关）
-1  = 方向完全相反
```

代码里的实现：

```python
dot = sum(x * y for x, y in zip(a, b))       # 点积：对应位置相乘再求和
norm_a = sum(x * x for x in a) ** 0.5         # 向量 A 的长度
norm_b = sum(x * x for x in b) ** 0.5         # 向量 B 的长度
if norm_a == 0 or norm_b == 0:
    return 0.0                                  # 零向量防御，避免除零
return dot / (norm_a * norm_b)                 # 点积 / (A的长度 × B的长度)
```

点积衡量"重叠程度"，长度做归一化，再加一个零向量防御——就这么简单。

在 RAG 场景中，通常：

- **> 0.8**：语义非常相似
- **0.5 ~ 0.8**：有关联
- **< 0.3**：基本无关

## 三、动手试试——看数据说话

运行 demo 前，确保 Ollama 已启动且模型已下载：

```bash
# 拉取模型（首次需要）
ollama pull qwen3-embedding:0.6b

# 运行 demo
python step1_embedding/demo.py
```

5 段文本，语义上有近有远：

| 编号 | 文本 | 语义类别 |
|------|------|---------|
| 1 | 盐湖股份2024年营业收入为150亿元，同比增长12%。 | 营收 |
| 2 | 盐湖股份2023年营收约134亿元，钾肥业务是主要收入来源。 | 营收 |
| 3 | 今天天气不错，适合出去散步。 | 天气 |
| 4 | 碳酸锂价格在2024年持续下跌，从年初的10万元/吨跌至年末的7万元/吨。 | 碳酸锂 |
| 5 | 盐湖股份的碳酸锂产能位居全国前列，2024年产量达到3.5万吨。 | 碳酸锂 |

运行后的余弦相似度矩阵（基于 qwen3-embedding:0.6b 实际运行结果）：

|       | 文本1 | 文本2 | 文本3 | 文本4 | 文本5 |
|-------|-------|-------|-------|-------|-------|
| 文本1 | 1.000 | 0.882 | 0.093 | 0.348 | 0.713 |
| 文本2 | 0.882 | 1.000 | 0.141 | 0.368 | 0.702 |
| 文本3 | 0.093 | 0.141 | 1.000 | 0.095 | 0.092 |
| 文本4 | 0.348 | 0.368 | 0.095 | 1.000 | 0.574 |
| 文本5 | 0.713 | 0.702 | 0.092 | 0.574 | 1.000 |

### 逐对解读

- **文本1 ↔ 文本2 = 0.882**：都说盐湖股份营收，语义高度相似 → 唯一超过 0.8 的对
- **文本1 ↔ 文本3 = 0.093**：一个说营收，一个说天气，几乎正交 → 接近 0，模型把"语义无关"做得很干净
- **文本4 ↔ 文本5 = 0.574**：都涉及碳酸锂，但一个讲价格下跌、一个讲产能，叙事方向不同 → 有关联但不算高
- **文本1 ↔ 文本5 = 0.713 > 文本4 ↔ 文本5 = 0.574**：这个结果初看反直觉——文本4和5都讲碳酸锂，为什么文本1和5反而更近？因为文本1和5都提到"盐湖股份"，**公司名是强语义锚点**，它的贡献盖过了"碳酸锂"这个品类词。这说明 Embedding 不是简单的"主题归类"，而是**多维语义叠加**——公司、品类、时间、数值等所有信号都在起作用

**这些关系不是人工标注的——它是模型从海量文本的统计共现规律中自动涌现的。**

### 相似度的边界——什么它做不好

数据看起来很美好，但余弦相似度有两个盲区，必须提前知道：

**1. 高相似度 ≠ 同义——否定的陷阱**

"盐湖股份2024年盈利"和"盐湖股份2024年亏损"只差一个字，余弦相似度可能高达 0.95+，但意思完全相反。Embedding 模型对否定的感知天生偏弱——因为"涨"和"跌"、"盈"和"亏"在训练语料中总是出现在相似的上下文里（都是讨论财务表现），模型倾向于把它们推到相近的位置。同理，"碳酸锂价格上涨"和"碳酸锂价格下跌"的相似度也会很高。

**2. 低相似度 ≠ 无关——因果与跨领域的弱信号**

反过来，相似度 0.3 也不一定不相关。两段文本如果分属不同领域但存在因果关系（"碳酸锂价格暴跌" vs "盐湖股份利润下滑"），或者表达方式差异大（口语 vs 书面语），相似度就可能落在这个区间。在我们的数据里也能看到，文本4（碳酸锂价格）和文本1（营收）相似度只有 0.348——但"碳酸锂价格下跌影响盐湖股份营收"恰恰是因果相关的。

**余弦相似度擅长捕捉"主题相近"，弱于捕捉"逻辑关系"和"否定翻转"。**

这也是为什么 RAG 检索用 Top-K 而不是硬阈值——宁可多召回几个再让 LLM 判断，也不要因为一个数字阈值漏掉关键文档。

## 四、Embedding 的定位

理解了 Embedding 本身，把它和两个"邻居"放一起对比，定位才清晰：一是传统检索（同样是"找文档"，但路线不同），二是 LLM（同样是"处理文本"，但角色不同）。

### 和传统检索比：稀疏 vs 稠密

如果你接触过搜索引擎，可能听说过 TF-IDF、BM25、倒排索引。它们和 Embedding 解决的是同一个问题——**把文本变成可以数学计算的表示，然后衡量相似度**。但路线完全不同。

**传统路线：稀疏表示（TF-IDF / BM25）**

TF-IDF 的思路很直接：**一个词在一篇文章里出现越多、在所有文章里出现越少，这个词就越重要。**

比如"营收"在这篇文档里出现了 5 次，在其他文档里很少出现 → "营收"是这篇文章的关键词。把所有关键词的重要性数值排成一排，就得到了一个向量——**稀疏向量**。

为什么叫"稀疏"？因为词表可能有几万个词，但一篇文档只涉及其中几十个。向量里绝大多数位置是 0，只有出现过的词才有值。

```
词表:  [营收, 利润, 碳酸锂, 天气, 足球, ...]
文档1: [3.2,  2.1,   0,     0,    0,   ...]   ← 只在"营收""利润"上有值
文档2: [0,    0,     2.8,   0,    0,   ...]   ← 只在"碳酸锂"上有值
```

**那查询时怎么打分？** TF-IDF 的相关性分数 = **TF × IDF**，两部分相乘：

- **TF（词频）**：查询词在这篇文档里出现得越多，越相关——"营收"出现 5 次的文档，比出现 1 次的更可能在讲营收
- **IDF（逆文档频率）**：一个词在越多文档里出现，区分度越低、权重越小——"的""是"几乎每篇都有，权重接近 0；"碳酸锂"只出现在少数文档里，权重很高

一篇文档对查询的得分，就是把查询里每个词的 TF×IDF 加起来——本质是"查询词在这篇文档里的加权命中次数"。BM25 是 TF-IDF 的升级版（词频做了饱和、再按文档长度归一化），打分思路一脉相承。

**倒排索引**就是这个稀疏向量的索引结构——记录"营收"这个词出现在哪些文档里，查询时直接反查，速度极快。

**Embedding 路线：稠密表示**

Embedding 的向量完全不同——**每个位置都有值，没有 0**：

```
（不再有词表的概念，只有 1024 个抽象维度）
文档1: [0.023, -0.157, 0.891, -0.015, ...]   ← 1024 个浮点数，每个都有值
文档2: [0.041, 0.083, -0.234, 0.067, ...]    ← 同样 1024 维
```

没有一个维度对应"营收"或"利润"——它们被编码在所有维度的组合里。

> **为什么几乎没有 0？** 可以把 1024 维想成 **1024 个"颜色通道"**——但和 RGB 三个通道不同，没有任何一个通道能单独解释含义，必须 1024 个一起看。训练时梯度下降会**反复微调整个向量**（每一维都在小幅变动），目标是把向量挪到空间中正确的位置，而不是像开关那样"打开"某几个维度、关掉其余的。关键在于：如果某一维长期停留在 0，就等于它没参与表达、白白浪费了一个维度——神经网络会倾向于**充分利用每一维**，所以最终几乎所有维度都是非零的小数，得到的就是稠密向量。

**核心区别**

|  | 稀疏表示（TF-IDF / BM25） | 稠密表示（Embedding） |
|---|---|---|
| **向量形式** | 每个维度=一个词，大部分是 0 | 1024 个抽象维度，每个都有值 |
| **怎么判断相关** | 查询词命中，按 TF-IDF/BM25 打分 | 查询向量与文档向量的余弦相似度 |
| **"营收"和"营业收入"** | 不同词 → 不同维度 → 无法关联 | 语义相近 → 向量相近 → 自然关联 |
| **索引结构** | 倒排索引（O(1) 查词） | 向量索引（ANN 近似最近邻） |
| **优势** | 精确匹配快、可控、可解释 | 理解语义、跨语言、容错 |
| **劣势** | 只能匹配字面、无法泛化 | 计算成本高、不可解释 |

> **什么是 ANN 近似最近邻？**
>
> Mini-RAG 当前检索时会把查询向量和库里每一个向量都算一遍余弦相似度——暴力遍历，数据少时没问题，但 100 万条就要算 100 万次。ANN 不再逐个点扫描，而是给向量建一张"近邻关系图"（常用 HNSW 算法）。可以把 HNSW 想成一个**带高速公路的导航系统**：Embedding 已经把文档摆到了"地图"上，查询时不挨个点找，而是利用"邻居关系 + 分层导航"从起点一步步跳到目标附近——把扫百万向量的检索，加速到只访问几百到几千个节点，速度提升几个数量级，召回率仍能保持 > 95%（代价是极小概率漏掉真正的最近邻）。

一句话：**稀疏表示是"字面指纹"，稠密表示是"语义指纹"。**

它们不是谁替代谁的关系——生产级 RAG 通常两者都用（混合检索），各取所长。Mini-RAG 当前只用了向量检索，把 BM25 也加进来做混合检索是后续可以演进的方向之一。

### 和 LLM 比：找 vs 答

很多初学者会问：既然 LLM 那么强，为什么不直接让它读所有文档、自己挑相关的？答案是**成本**。

LLM 判断一篇文档相不相关，得真正读懂它——逐 token 算一遍，让 LLM 把百万篇文档都读一遍去筛，成本高到不现实。而 Embedding 能在**文档入库时就离线算好向量**，查询时只需算一次查询向量、再做检索，极快极便宜。

|  | Embedding 模型 | LLM |
|---|---|---|
| **怎么判断相关** | 比向量远近（不读内容，快而便宜，可离线预计算） | 真正读懂文档（慢而贵） |
| **回答的问题** | "哪些**可能**相关？" | "这些**真的**回答了问题吗？"+ 组织答案 |
| **在 RAG 中** | **找（召回）**：从全库粗筛 Top-K | **答（精排+生成）**：读懂 Top-K 再作答 |

学术上把 Embedding 这一步叫**召回（Recall）**——它不真正理解文档内容，只看向量远近，宁可多召回几个、保证不漏；LLM 再来判断这些文档"真的相关吗"并组织成答案。一个重召回率（不漏），一个重理解（答得对）。

> Mini-RAG 是朴素版：Embedding 召回 Top-K 后直接交给 LLM 生成。现代 RAG 通常在召回和生成之间再插一层**精排**——召回用的是"双塔"模型（查询和文档**分别**编码成向量再比相似度，快但粗，适合从百万文档里粗筛）；精排换成 Cross-Encoder（把查询和文档**拼在一起**送进模型，让它同时读两者、判断到底相不相关，准但慢），把召回的 Top-100 压到 Top-10 再喂 LLM。一句话：**召回要快（粗筛），精排要准（细筛）**。

少了谁都不行：只用 LLM，受限于上下文窗口和成本，没法把整个文档库都喂给它逐篇筛选；只用 Embedding，它只会算相似度把文档找出来，读不懂内容、也组织不出答案。

### 小结

> Embedding 把一段文本压成一个 1024 维向量，语义相近则坐标相近；用余弦相似度算远近，但它擅长"主题相近"、弱于"否定翻转"和"逻辑关系"，所以 RAG 用 Top-K 召回而非硬阈值。这套语义是模型从海量语料预训练里带出来的——和 BM25 当场数字面词频不同，和 LLM 逐字生成答案也不同。RAG 的分工很清晰：**Embedding 负责"找"，LLM 负责"答"**。
