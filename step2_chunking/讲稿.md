# Step 2 讲稿：文档分块 —— 理解 Chunking

---

## 一、为什么要把文档分块

[Step 1](../step1_embedding/讲稿.md) 我们把"一句话"变成了向量。但真实文档不是一句话——一份年报几十页，一篇研报上万字。RAG 要怎么处理这种长文档？

最直觉的做法：把整篇文档压成一个向量，存进向量库。但这样做有三个问题：

- **信息稀释**：一篇年报既讲营收、又讲产能、又讲风险、又讲展望。一个 1024 维向量要同时表达这么多主题，结果哪个都表达不清楚——向量变成"什么都说了一点，但什么都不像"的模糊平均。检索时，无论你问营收还是产能，匹配到的都是同一个糊掉的向量。
- **检索粒度太粗**：用户问"盐湖股份碳酸锂产能多少"，你只能返回整篇年报。但 LLM 要的是"产能 3.5 万吨"那一句，不是几十页 PDF。
- **超输入上限**：embedding 模型一次能处理的文本长度有上限（几千个 token）。几十页的年报远超这个上限，整篇根本喂不进去。

**解决办法就是分块（chunking）——把长文档切成一个个小段（chunk），每个 chunk 单独变成一个向量。** chunk 就成了 RAG 的检索单位：

```
用户提问 → 算查询向量 → 在所有 chunk 向量里找最相似的 Top-K → 把这几个 chunk 喂给 LLM 答题
```

> **chunk ≠ embedding 模型的最大输入。** 这两个概念很容易混。qwen3-embedding 的上下文窗口是 8k+ token——理论上能吞下很长的一段文本。但 RAG 里一个 chunk 通常只放 200~500 token，远小于这个上限。为什么切这么小？因为 chunk 同时也是"喂给 LLM 的上下文单位"——检索回来 5 个 chunk，每个 400 token，加起来 2000 token 刚好塞进 LLM 的上下文窗口。chunk 太大，Top-5 就把窗口撑爆了；chunk 太小，单块语义又残缺。chunk_size 是在这几个约束之间权衡出来的应用层粒度，不是模型能力的上限。

这一章要回答三个工程问题：**怎么切？切多大？切分边界怎么处理？**

---

## 二、怎么切：递归切分

知道了为什么要分块，这一节回答第一个问题：**怎么把文档切成块**。

### 最朴素：固定字符切分

硬按 `chunk_size` 个字符切一刀。简单，但有个致命缺陷——它不管句子边界，会把一句话从中间劈开。看演示 1（`split_fixed`，chunk_size=40）：

```
[1] (40字) 盐湖股份2024年实现营业收入150亿元，同比增长12%；归母净利润45亿元，同
[2] (40字) 比增长20%。公司业绩增长主要得益于钾肥价格回暖与碳酸锂产销两旺。年报显示，公司
```

块 1 结尾是"同"，块 2 开头是"比增长"——**"同比增长"这个词被劈成了两半**。再往下，"2024 年"也被劈成"2"和"024 年"。被劈开的句子，前后两块都语义残缺。

### 更好：递归切分（recursive splitting）

核心思想是**尽量在语义边界切**：先试段落边界（`\n\n`），切出的块还太大就退到句子边界（句号），再不行退到更细的（逗号），最后兜底按字符硬切。

实现就是一个按优先级排列的分隔符列表：

```python
separators = ("\n\n", "\n", "。", "！", "？", "；", "，", " ", "")
#              段落   换行  句号  感叹  问号  分号  逗号  空格  字符
#              ←——————————— 优先级从高到低 ———————————→
```

切分算法（`demo.py` 里的 `RecursiveTextSplitter`，思路同 langchain 的 `RecursiveCharacterTextSplitter`）：

1. 从最高优先级开始，找第一个**出现在文本里**的分隔符
2. 用它把文本切开
3. 对每个切出的小块：
   - 够小（`<= chunk_size`）→ 收下
   - 还太大 → 用**下一级**分隔符递归切它
4. 所有分隔符都试过还不够小 → 兜底按字符硬切

为什么这样好？因为它**优先在最大的语义单元边界切**，只有不得已才往更细的边界退。绝大多数 chunk 都能完整落在段落或句子的边界上。看演示 2（递归切分，chunk_size=80）：

```
递归 chunk_size=80  →  共 11 块
  [1] (73字) 盐湖股份2024年实现营业收入150亿元，同比增长12%...产销两旺。
  [2] (52字) 年报显示，公司整体毛利率...钾肥是公司的传统主业，产能位居全国前列。
  [3] (63字) 2024年氯化钾产量约500万吨...是业绩的压舱石。
  [4] (74字) 报告期内，公司推进百万吨钾肥扩建项目...产能位居全国前列。
  ...（共 11 块）
```

每块都是完整的句子，没有半句话。对比演示 1，差距立现。

### 代码三个关键点

**`_split` 的递归**——核心就是这个"太大就降级"的逻辑：

```python
piece = part + chosen              # 把分隔符加回块尾，合并时能还原原文
if len(piece) <= self.chunk_size:
    pieces.append(piece)           # 够小，直接收
else:
    pieces.extend(self._split(piece, rest))   # 太大，换更细的分隔符继续切
```

分隔符列表末尾的空串 `""` 是字符级兜底：递归到它时直接按 `chunk_size` 硬切，保证再大的块也能切到 `<= chunk_size`。所以这里只有两个分支——要么够小直接收，要么 `rest` 里还有更细的分隔符可以继续切（最终一路兜底到空串硬切），不需要"切不动就整块收"的第三分支。

**跳过纯空白 part**——递归到句子层时，上层遗留的段落分隔符 `\n\n` 会被 `split("。")` 暴露成空白残片（如 `\n`），不跳过就会包成 `"\n。"` 这种垃圾块混进来：

```python
for part in text.split(chosen):
    if not part.strip():           # 跳过纯空白，避免 \n\n 残片污染
        continue
```

**`_merge` 把小块拼成 chunk**——注意 `_split` 只保证每块落在语义边界（不劈句子），**不保证每块都接近 `chunk_size`**：切出的块可能远小于 `chunk_size`（一个短句才 20 字）。如果就这么留着，一块就一个短句，块数爆炸、每块语义单薄。所以 `split_text` 是**两步**——`_split` 先切出"落在语义边界的小块"，`_merge` 再把相邻小块累积拼接，凑成接近 `chunk_size` 的 chunk：

```python
for p in pieces:
    if cur and cur_len + len(p) > self.chunk_size:   # 再拼这块要超了
        chunks.append("".join(cur))                   # 把已累积的封成一个 chunk
        # （封完后还会留一段 overlap，下一节展开）
    cur.append(p)
    cur_len += len(p)
```

一句话概括这个分工：**`_split` 保边界，`_merge` 凑大小**。

> 这是教学简化版。生产级实现（如 langchain）还会做 **markdown 结构感知切分**——识别标题、列表、代码块，按文档结构切而不是纯按分隔符，切出来的块更贴合原文组织。

## 三、切多大：chunk_size 的权衡

会切了，下一个问题：**切多大合适**？

`chunk_size` 决定每个 chunk 多长（本项目按字符数算）。它是个两难：

**太小**

- 单块语义不全——一句话被拆成两块，每块都缺主语或缺结论
- 检索碎——同一个信息点散落在多个小块里，召回时可能只命中半个
- 块数爆炸——一篇文档切成上千块，向量库膨胀，检索变慢

**太大**

- 信息稀释——回到"整篇压一个向量"的老问题，一个 chunk 塞太多主题，向量糊
- 定位不准——检索到的 chunk 太长，LLM 要在里面翻找答案
- 挤占上下文——Top-K 个大 chunk 很快撑爆 LLM 上下文窗口

经验值：**中文通常 200~500 字，英文 256~512 token**。但这不是铁律——财报、法律条文、对话记录，最佳 chunk_size 都不同，实际项目要拿自己的数据试。

跑一下 demo 看对比（`RecursiveTextSplitter` 切一段约 670 字的盐湖股份年报文本，三档 chunk_size）：

```
递归 chunk_size=40   →  共 24 块（碎）
  [1]  (29字) 盐湖股份2024年实现营业收入150亿元，同比增长12%；
  [9]  (14字) 碳酸锂是公司的第二增长曲线。
  ...（一句甚至半句一块，共 24 块）

递归 chunk_size=200  →  共 5 块（合适）
  [1] (107字) 盐湖股份2024年...盈利能力持续改善。   ← 业绩
  [2] (118字) 钾肥是公司的传统主业...巩固产能优势。  ← 钾肥
  [3] (126字) 碳酸锂是公司的...保持盈利。           ← 碳酸锂
  ...（每块聚焦一个主题，共 5 块）

递归 chunk_size=800  →  共 1 块（糊）
  [1] (673字) （整篇年报塞进一块）
```

`chunk_size=40` 把每句话甚至半句拆成一块——块数爆炸、检索碎，单块还可能缺上下文（比如光看到"钾肥产能位居全国前列"却不知道在说哪家公司）。`chunk_size=800` 把整篇塞一块——回到第一节"整篇压一个向量"的信息稀释。**40 太碎，800 太糊，中间才是甜区**——`chunk_size=200` 每块聚焦一个主题（业绩 / 钾肥 / 碳酸锂 / 展望），正好落在经验值的甜区里。

## 四、overlap：边界不断义

递归切分解决了"切断句子"，但还有个边界问题：

假设一句话恰好横跨两个 chunk 的切分点——比如"盐湖股份依托察尔汗盐湖，具备低于同业的成本优势"，前半句在 chunk A，后半句在 chunk B。用户问"盐湖股份的成本优势"，这句的关键信息被劈成两半，A 和 B 单独看都不完整，检索可能两边都召回不全（或召回回来 LLM 也拼不出完整意思）。

**overlap（重叠）**就是对策：相邻 chunk 之间共享一段重叠内容。chunk B 不从 A 的结尾之后开始，而是**回退一段**，把 A 的结尾部分也包含进来：

```
chunk A: [████████████████████]
chunk B:          [████████████████████]   ← 开头和 A 的结尾重叠
chunk C:                   [████████████████████]
```

这样横跨边界的句子，至少有一个 chunk 能完整包含它。代价是存储和计算略增（重叠部分被向量化了两次），以及检索时同一个信息可能命中两个相邻 chunk（去重即可）。overlap 通常设 `chunk_size` 的 10%~20%。

看演示 4（chunk_size=100，对比 overlap=0 vs 50；50% 是为夸张展示重叠效果，实际通常 10~20%）：

```
overlap=0  →  共 9 块
  [1] (73字) 盐湖股份2024年...产销两旺。
  [2] (87字) 年报显示...市场份额持续领先。
  ...

overlap=50  →  共 12 块
  [1] (73字) 盐湖股份2024年...产销两旺。
  [2] (78字) 公司业绩增长主要得益于钾肥价格回暖与碳酸锂产销两旺。年报显示...产能位居全国前列。
              ↑ 块 2 开头复述了块 1 的结尾句"公司业绩增长...产销两旺。"
  ...
```

`overlap=0` 的块 2 从"年报显示"开始；`overlap=50` 的块 2 回退了一句，把块 1 结尾的"公司业绩增长...产销两旺。"也包进来——这句横跨块 1/块 2 边界的话，现在块 2 里完整了。

**overlap 在 `_merge` 里怎么实现**——上一节 `_merge` 封完一个 chunk 后，**并不把累积清空**，而是从开头弹出若干块、只留一段长度 `<= chunk_overlap`：

```python
chunks.append("".join(cur))                   # 封一个 chunk
while cur and cur_len > self.chunk_overlap:    # 从开头弹出，留一段 <= overlap
    cur_len -= len(cur[0])
    cur.pop(0)
```

下一个 chunk 接着这段剩余内容开始累积，于是相邻两个 chunk 共享了这段 `<= overlap` 的内容——边界处的句子，两个 chunk 都能完整包含。`chunk_overlap=0` 时这个 `while` 一次都不进，全部弹光，相邻块互不重叠。

## 五、小结

> 分块是 RAG 的第一道工序：把长文档切成 `chunk_size` 大小的块，每块单独向量化。递归切分按"段落 → 句子 → 字符"的优先级找语义边界，避免硬切句子；`chunk_size` 在"太小语义碎 / 太大信息糊"之间权衡（中文经验 200~500 字）；`overlap` 让相邻块共享一段，防止关键信息卡在切分边界。**chunk 是 RAG 的检索单位——它的大小和切法，直接决定检索能不能找得准、LLM 能不能答得好。**
